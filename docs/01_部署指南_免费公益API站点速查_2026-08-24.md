## 一、项目概述

### 1.1 技术栈

| 维度 | 技术 |
|------|------|
| 前端框架 | **无框架** — 纯原生 HTML + CSS + JavaScript |
| 构建工具 | **无构建步骤**（零依赖、零 npm install） |
| 数据源 | `broadcast/data/sites.json` + `notice.md`（运行时 `fetch` 加载） |
| 主题系统 | CSS 变量 + `localStorage` 持久化，支持亮/暗/跟随系统 |
| 部署方式 | GitHub Pages（GitHub Actions 自动部署） |
| 域名解析 | Cloudflare DNS（CNAME → `qwdingyu.github.io`） |
| SSL 证书 | Let's Encrypt（GitHub Pages 自动签发，90天自动续期） |

### 1.2 架构原理

```
浏览器请求 → free.eforge.xyz
  → Cloudflare DNS (CNAME)
  → qwdingyu.github.io (GitHub Pages)
  → GitHub Actions 自动部署
  → 静态文件 (HTML + CSS + JS + JSON)
```

核心工作流：
1. `broadcast/index.html` 渲染页面骨架
2. `broadcast/app.js` 客户端 JS 加载
3. `fetch("./data/sites.json")` 运行时加载站点数据
4. `fetch("./data/notice.md")` 运行时加载公告
5. DOM 渲染卡片列表 + 搜索/筛选/主题切换

**关键点**：数据完全在客户端加载和渲染，无后端、无数据库、无 API 调用。

## 二、部署步骤（完整复现）

### 2.1 创建 GitHub 仓库

```bash
gh repo create qwdingyu/sk-free --public --description "TOKEN 站点速查 - 静态导航站"
```

### 2.2 修改 HTML 文件

**文件 1**：`index.html`（根页面重定向）

```html
<!-- 修改前 -->
<meta http-equiv="refresh" content="0; url=./broadcast/" />

<!-- 修改后（兼容 GitHub Pages Actions 部署） -->
<meta http-equiv="refresh" content="0; url=./broadcast/index.html" />
```

**文件 2**：`broadcast/index.html`（OG 标签 + hero 文案）

```html
<!-- 修改 OG 标签 -->
<meta property="og:url" content="https://free.eforge.xyz/broadcast/" />

<!-- 修改 hero 文案 -->
<p class="eyebrow">FREE.EFORGE.XYZ</p>
```

**文件 3**：`index.html`（根页面 OG 标签）

```html
<meta property="og:url" content="https://free.eforge.xyz/" />
```

### 2.3 创建 CNAME 文件

在仓库根目录创建 `CNAME` 文件，内容为自定义域名：

```
free.eforge.xyz
```

### 2.4 创建 GitHub Actions 工作流

文件：`.github/workflows/deploy.yml`

```yaml
name: Deploy to GitHub Pages

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: false

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with:
          path: .
      - id: deployment
        uses: actions/deploy-pages@v4
```

### 2.5 推送代码

```bash
git remote add deploy https://github.com/qwdingyu/sk-free.git
git add -A
git commit -m "初始化部署"
git push deploy main
```

### 2.6 启用 GitHub Pages

```bash
gh api repos/qwdingyu/sk-free/pages -X POST -f build_type=workflow
```

### 2.7 设置自定义域名

```bash
gh api repos/qwdingyu/sk-free/pages -X PUT -f build_type=workflow -f cname=free.eforge.xyz
```

### 2.8 配置 Cloudflare DNS

在 Cloudflare Dashboard 中：
1. 选择 `eforge.xyz` 域名
2. DNS → Records → Add record
3. Type: `CNAME`，Name: `free`，Target: `qwdingyu.github.io`
4. **Proxy status: 必须关闭**（灰色云朵，DNS only）
5. TTL: Auto

## 三、踩坑记录与注意事项

### 3.1 ⚠️ 根路径重定向 404 问题

**现象**：`/broadcast/` 返回 404，但 `/broadcast/index.html` 返回 200。

**原因**：GitHub Pages 使用 Actions 部署时，**不自动 serve 目录下的 `index.html`**（与传统 GitHub Pages 的 branch 部署行为不同）。

**修复**：将根 `index.html` 的重定向从 `./broadcast/` 改为 `./broadcast/index.html`。

```html
<!-- 修复前 -->
<meta http-equiv="refresh" content="0; url=./broadcast/" />

<!-- 修复后 -->
<meta http-equiv="refresh" content="0; url=./broadcast/index.html" />
```

### 3.2 ⚠️ CNAME 文件不被 Actions 部署自动识别

**现象**：CNAME 文件存在于仓库中，但 `gh api repos/.../pages` 返回 `cname: null`。

**原因**：`actions/deploy-pages` 不会自动读取 CNAME 文件来设置自定义域名。

**修复**：必须通过 API 显式设置：

```bash
gh api repos/qwdingyu/sk-free/pages -X PUT -f build_type=workflow -f cname=free.eforge.xyz
```

### 3.3 ⚠️ 首次部署时序问题

**现象**：第一个 workflow run 失败，报 `Get Pages site failed`。

**原因**：workflow 在 Pages 功能完全启用之前就触发了。

**修复**：
1. 先通过 API 启用 Pages
2. 再推送包含 workflow 的代码
3. 如果仍然失败，用 `gh run rerun <run-id> --failed` 重试

### 3.4 ⚠️ SSL 证书签发延迟

**现象**：部署完成后立即访问，浏览器显示"不安全"警告。

**原因**：Let's Encrypt 证书签发需要时间（通常 1-5 分钟），期间 GitHub Pages 使用临时证书。

**验证方法**：

```bash
# 检查证书状态
gh api repos/qwdingyu/sk-free/pages | python3 -c "
import json,sys
d=json.load(sys.stdin)
cert = d.get('https_certificate', {})
print(f'Cert state: {cert.get(\"state\")}')  # 应为 approved
"
```

**结论**：这是正常现象，等待 1-5 分钟即可。证书签发后自动生效。

### 3.5 ⚠️ GitHub Pages OAuth Token 权限不足

**现象**：使用 wrangler 的 OAuth Token 调用 Cloudflare DNS API，返回 `Invalid access token`。

**原因**：wrangler 的 OAuth Token 权限范围是 Workers/Pages/D1，不包含 DNS 编辑权限。

**解决**：需要在 Cloudflare Dashboard 手动添加 DNS 记录，或创建具有 `Zone:DNS:Edit` 权限的 API Token。

### 3.6 ⚠️ Fork vs 新建仓库的决策

**选择新建仓库的理由**：
1. 原仓库 82 条提交大部分是自动更新，保留历史价值不大
2. 部署到自己的域名，不需要原作者的 upstream 同步
3. 新仓库更干净，没有 fork 标记
4. 数据文件 100% 会替换成自己的内容

**唯一选 fork 的场景**：需要拉取原作者新增的站点数据。但这完全可以手动复制 `sites.json` 的变更。

## 七、与 Cloudflare Workers 部署的对比

| 维度 | 本项目 (GitHub Pages) | Cloudflare Workers |
|------|----------------------|-------------------|
| 成本 | **完全免费** | 免费额度 10万请求/天，超出 $0.30/百万 |
| 冷启动 | **无**（静态文件直接返回） | 有（V8 isolate 启动） |
| 数据更新 | 改 JSON → git push → 自动部署 | 需要 KV/R2 存储 + API 更新 |
| 复杂度 | **极低**（零依赖） | 需要 Workers + KV/R2 绑定 |
| SEO | 完整 HTML 输出，爬虫友好 | 同样可以，但需要额外配置 |
| 离线可用 | 首次加载后可离线访问 | 不行 |
| 数据一致性 | Git 版本控制，可追溯 | 需要额外实现版本管理 |
| 适用场景 | 数据量小、更新频率中等 | 数据量大、需要动态查询/写入 |

**结论**：对于"JSON 驱动的静态导航/目录站"，GitHub Pages 是最佳选择——零成本、零运维、Git 即 CMS。
