# 03 部署流程与自动化指南

> 日期：2026-08-24
> 状态：待实施

## 一、部署架构总览

sk-free 采用**双轨部署**架构：

| 组件 | 部署目标 | 触发方式 | 说明 |
|------|----------|----------|------|
| 前端（静态站点） | GitHub Pages | git push → GitHub Actions | HTML/CSS/JS |
| 投票 API | Cloudflare Workers | `wrangler deploy` | Worker + KV |

## 二、前端部署（GitHub Pages）

### 2.1 部署流程

```
本地修改 → git push deploy main → GitHub Actions 触发 → 自动部署
                ↓
        .github/workflows/deploy.yml
                ↓
        actions/upload-pages-artifact@v3
                ↓
        actions/deploy-pages@v4
                ↓
        https://free.eforge.xyz/
```

### 2.2 关键配置

| 文件 | 作用 |
|------|------|
| `CNAME` | 自定义域名绑定（必须在仓库根目录） |
| `.github/workflows/deploy.yml` | GitHub Actions 部署工作流 |
| `index.html`（根目录） | 重定向到 `./broadcast/index.html` |

### 2.3 注意事项

1. **CNAME 必须在仓库根目录**：GitHub Pages 要求 CNAME 文件在根目录，否则自定义域名失效
2. **目录索引 404**：GitHub Pages Actions 部署不会自动为目录路径提供 index.html，必须使用显式路径 `/broadcast/index.html`
3. **首次部署需手动触发**：Pages 配置完成后，可能需要手动重跑失败的 Actions

### 2.4 常用命令

```bash
# 查看部署状态
gh run list --repo qwdingyu/sk-free --limit 5

# 查看最新部署日志
gh run view --repo qwdingyu/sk-free --log

# 手动触发部署
gh workflow run deploy.yml --repo qwdingyu/sk-free

# 重跑失败的部署
gh run rerun <run-id> --failed --repo qwdingyu/sk-free
```

## 三、投票 Worker 部署（Cloudflare Workers）

### 3.1 首次部署

```bash
# 1. 登录 Cloudflare
cd worker/
npx wrangler login

# 2. 创建 KV 命名空间
npx wrangler kv:namespace create SKFREE_KV
# 输出示例：
# { "binding": "SKFREE_KV", "id": "abc123..." }
# 将 id 填入 wrangler.toml 的 [[kv_namespaces]] 段

# 3. 部署 Worker
npx wrangler deploy
# 输出示例：
# Published sk-free-vote (xxx)
# https://sk-free-vote.xxx.workers.dev

# 4. 将 Worker URL 填入前端 app.js 的 VOTE_API_URL 常量
```

### 3.2 日常部署

```bash
cd worker/
npx wrangler deploy
```

### 3.3 KV 数据管理

```bash
# 查看 KV 命名空间列表
npx wrangler kv:namespace list

# 读取投票数据
npx wrangler kv:key get --namespace-id <id> votes.json

# 写入测试数据
npx wrangler kv:key put --namespace-id <id> votes.json '{"测试站点":{"up":5,"down":1}}'

# 清空投票数据
npx wrangler kv:key delete --namespace-id <id> votes.json
```

## 四、一键部署脚本 deploy.sh

### 4.1 设计思路

参考 cf-shop 的 `local-deploy.sh` 模式，针对 sk-free 的纯静态特性进行了简化：

| cf-shop（复杂应用） | sk-free（纯静态） |
|---------------------|-------------------|
| npm install | 无依赖 |
| npm run frontend:build | 无构建步骤 |
| 数据库迁移 | 无数据库 |
| wrangler deploy（含 secrets） | wrangler deploy（仅 KV） |
| 多步验证 | JSON 校验 + CNAME 检查 |

### 4.2 使用方式

```bash
# 仅推送到 GitHub Pages
bash deploy.sh

# 同时部署投票 Worker
bash deploy.sh --worker
```

### 4.3 执行步骤

```
步骤 1/4：校验 sites.json（JSON 语法 + 字段完整性）
步骤 2/4：校验 CNAME（存在性 + 域名非空）
步骤 3/4：Git 操作（status → add → commit → push）
步骤 4/4：部署 Worker（可选，--worker 参数启用）
```

### 4.4 脚本特性

- **自动提交信息**：检测 sites.json 变更时自动生成包含站点数的提交信息
- **交互式确认**：有变更时询问是否提交，避免误操作
- **JSON 校验**：部署前校验 sites.json 语法和字段完整性
- **CNAME 保护**：防止 CNAME 文件丢失导致域名失效
- **KV 自动创建**：首次部署 Worker 时自动创建 KV 命名空间

## 七、常见问题

### Q: 推送后 GitHub Actions 没触发？

A: 检查以下几点：
1. `deploy.yml` 是否在 main 分支的 `.github/workflows/` 下
2. GitHub Pages 是否已启用（Settings → Pages → Source: GitHub Actions）
3. 手动触发：`gh workflow run deploy.yml --repo qwdingyu/sk-free`

### Q: 自定义域名 SSL 不安全？

A: Let's Encrypt 证书自动签发需要几分钟。等待后刷新即可。如果持续不安全：
1. 检查 CNAME 文件内容：`cat CNAME`
2. 检查 DNS 解析：`dig free.eforge.xyz`
3. 检查 GitHub Pages 设置中的自定义域名

### Q: Worker 部署后 CORS 报错？

A: 检查 Worker 代码中的 `ALLOWED_ORIGINS` 数组是否包含你的前端域名。

### Q: 投票数据丢失？

A: KV 数据是持久化的，不会丢失。如果需要重置：
```bash
npx wrangler kv:key delete --namespace-id <id> votes.json
```
