## 1. 🔴 P0：HEAD 探测会把活着的高价值站点自动下线

### 1.1 实测证据

对 `/api/sites` 返回的全部 18 个 URL 做实测（`curl -I -L`，UA 与 `health.js:26` 一致）：

| 结果 | 条数 |
|---|---|
| HEAD 返回 200，0 次重定向 | **17** |
| **HEAD 挂起，5 秒后连接被丢弃（`code=000`）** | **1** |

失败的那一条是 `https://agentrouter.org/register?aff=l1gl`。单独复测：

```
HEAD  /register?aff=l1gl   →  code=000  t=5.008   （挂起后断开）
GET   /register?aff=l1gl   →  code=200  t=2.484   ← 站点完全正常
HEAD  /                    →  code=200  t=1.271   ← 根域的 HEAD 是好的
GET   /                    →  code=200  t=1.369
```

**这个站活得很好，只是这个具体路径不处理 HEAD 请求。**

### 1.2 后果链条（全自动、无人工确认、首页无痕迹）

```
health.js:22  method:"HEAD"           →  AgentRouter 超时
health.js:39  返回 { ok:false, error:"timeout" }
health.js:70  列入 newDeadUrls
index.js:528  前端自动调 dead-urls/batch { action:"add" }   ← 无二次确认
deadurls.js:74  UPDATE sites SET enabled = 0                ← 自动停用
sites.js:96   从 /api/sites 结果里 filter 掉                 ← 首页消失
```

**AgentRouter 是整个数据集里额度最高的两条之一（每日 25 刀）。** 管理员点一次「🧹 一键清理死链」或「批量检查」，它就会静默下线，而首页不会留下任何痕迹——用户只会觉得"收录变少了"。

### 1.3 把超时从 1500 改到 8000 治不了这个病

`worker/index.js:821-822` 的改动注释写"1.5 秒太短导致大量合法站点误判为死链"：

```js
const result = await checkBatchHealth(db, urls, 8000);
```

方向对，但 AgentRouter 是 **5 秒就被对端断开连接**，不是慢。8000ms 只是让它等更久，然后**同样判死**。这不是超时问题，是 **HEAD 语义问题**。

### 1.4 还有两类未被实测覆盖但逻辑上必然误判的情况

`health.js:31` 的存活判定是：

```js
ok: res.status >= 200 && res.status < 400
```

| 状态码 | 真实含义 | 当前判定 |
|---|---|---|
| `405 Method Not Allowed` | 服务器活着，只是不支持 HEAD | ❌ 判死 |
| `403 Forbidden` | 通常是 WAF / Cloudflare 挡爬虫，站点活着 | ❌ 判死 |
| `501 Not Implemented` | 同 405 | ❌ 判死 |
| `429 Too Many Requests` | 活着，只是限流 | ❌ 判死 |

当前 18 条里没有出现这些码，所以**这一段是逻辑推演，不是实测到的故障**。但免费 API 站点大量挂在 Cloudflare 后面，403 只是时间问题。

### 1.5 修法（按性价比排序）

| # | 改动 | 代价 | 效果 |
|---|---|---|---|
| 1 | **HEAD 失败时 fallback 一次 `GET` + `Range: bytes=0-0`** | 每个失败 URL 多 1 个 subrequest（只对少数生效） | 直接修掉 AgentRouter 这类问题 |
| 2 | **放宽判定**：`403/405/429/501` 视为存活（能回状态码就说明服务器在） | 改一行 | 修掉 1.4 的四类误判 |
| 3 | **自动下线改为"待确认"**：新增 `suspect` 状态，或要求连续 N 次（如 3 次）失败才停用 | 加一列 + 计数逻辑 | **单次网络抖动不再让站点消失**——这是最重要的一条 |
| 4 | 移除前端的自动 `action:"add"`（`index.js:528`、`index.js:558`），改成列出结果由管理员勾选确认 | 改前端 | 把不可逆的自动操作变成可审阅的操作 |

**第 3 条最关键。** 健康检查是概率性的（网络抖动、对端限流、CF 挑战），把概率性信号直接接到不可逆的下线动作上，架构上就是错的。

### 1.6 顺带修正我在 docs/08 附录 A.2 里的一处推测

我在 A.2 里担心 `redirect: "follow"`（`health.js:23`）会让重定向跳数额外消耗 subrequest，从而使"48 fetch = 49 subreq"的算法失效。

**实测 18 条 URL 全部是 0 次重定向**，所以这个担忧在当前数据下不成立。保留为将来的注意事项（新增站点若有 http→https 跳转会触发），但**不作为当前问题**。A.2 里关于 D1 写入未计入余量的那部分仍然成立。

## 2. 🔴 P0/P1：改名和删除站点都会产生孤儿反馈

`worker/migrations/0002_add_feedbacks_up.sql:10` 用 `site_name TEXT NOT NULL` 关联站点——和 `votes` 一样是"名字当外键"。但配套的引用维护**只做了一半**：

| 操作 | `votes` | `dead_urls` | `feedbacks` |
|---|---|---|---|
| 改名（`sites.js:242-255` 原子 batch） | ✅ `UPDATE votes SET site_name = ?` | 不需要（按 url 关联） | ❌ **漏了** |
| 删除（`sites.js:296-300`） | ✅ `DELETE FROM votes` | ✅ `DELETE FROM dead_urls` | ❌ **漏了** |

核实命令：

```
sed -n '240,256p' worker/src/sites.js | grep -c feedbacks   →  0
grep -A12 handleAdminDeleteSite worker/src/sites.js | grep "DELETE FROM"
  → DELETE FROM sites / DELETE FROM votes / DELETE FROM dead_urls   （无 feedbacks）
```

**后果：**

1. 改名后，历史反馈的 `site_name` 仍是旧名。Admin 反馈列表（`index.js:591` `esc(f.siteName)`）显示一个已不存在的站名，管理员无法定位到站点。
2. 删除站点后，反馈永久残留，且 Admin 面板里点不到对应站点。
3. `feedbacks.js:59-62` 提交时校验站点必须存在——所以**旧名的反馈只读不可写**，形成一批既无法处理也无法关联的死数据。

**注意改名的实现是 DELETE + INSERT**（`sites.js:243-246`），不是 `UPDATE sites SET name`。所以 `id INTEGER PRIMARY KEY AUTOINCREMENT` 每次改名都会变（`created_at` 手工保留了，id 没有）。任何以 id 做关联的将来设计都会被这个实现打断。

**修法**：短期在改名 batch 和删除路径各补一条 `feedbacks` 语句（**S**，10 分钟）。长期按 `docs/09` 阶段 A 引入 `slug`，把 `votes`/`feedbacks`/`submissions` 全部改成引用 `slug`，改名不再牵动任何关联表（**M**）。

## 3. 🟠 P1：`feedbacks.type` 的 CHECK 约束会挡住 docs/10 自己提的建议

`0002_add_feedbacks_up.sql:11`：

```sql
type TEXT NOT NULL CHECK(type IN ('error', 'correction', 'positive')),
```

而 `docs/10:143-151` 建议把「👍 还能用 / 💀 已失效」一键反馈提前到阶段 0，实现方式是"复用现有 `/api/feedback`，`type` 加 `still_works` / `dead`"。

**这两件事直接冲突：SQLite 不支持修改 CHECK 约束。** 加这两个 type 必须重建整张表（`CREATE TABLE feedbacks_new` → `INSERT INTO ... SELECT` → `DROP` → `RENAME`），是一次真实的 migration，不是"1 小时内可完成"。

三个选择：

| 方案 | 代价 | 评价 |
|---|---|---|
| A. 现在就重建表，把 5 个 type 一次加齐 | 一次 migration（**S**，趁数据量小） | **推荐**。反馈表现在几乎是空的，重建成本最低，越往后越贵 |
| B. 去掉 CHECK 约束，改在应用层用 `VALID_TYPES`（`feedbacks.js:14`）校验 | 改 DDL + 已有校验代码不动 | 可行。应用层校验已经存在且更灵活 |
| C. 「还能用/已失效」不走 feedbacks，单独建 `site_signals` 表 | 新表（**M**） | 语义更干净（信号 ≠ 反馈，且信号要计数聚合），但工作量大 |

我的建议是 **A 或 B，趁现在表是空的做掉**。反馈和"还能用"信号的读写模式确实不同（前者要逐条处理，后者要聚合计数），但为 18 条数据的站点建两张表不值得——先合并，等信号量真的上来再拆。

## 5. ✅ 做对了的地方（值得保留为范式）

### 5.1 `feedbacks.js` 的限流写法是正确的，而 `submissions.js` 的是错的

这两处放在一起看特别有教学价值：

```js
// ✅ feedbacks.js:47 — 正确：把 epoch 转成 datetime 再比
"SELECT COUNT(*) as count FROM feedbacks WHERE ip = ? AND created_at > datetime(?, 'unixepoch')",
[ip, Math.floor((now - FEEDBACK_RATE_WINDOW_MS) / 1000)]

// ❌ submissions.js:44 — 错误：用 epoch 毫秒字符串直接比 datetime 字符串
"SELECT id FROM submissions WHERE ip = ? AND created_at > ?",
[ip, (now - SUBMIT_RATE_WINDOW_MS).toString()]
```

`created_at` 是 `datetime('now')` 产出的 `"2026-08-25 00:40:40"`。SQLite 做字符串比较时 `"2…"` 恒大于 `"1756…"`，所以 `submissions.js` 的窗口永不生效——**每个 IP 的 5 次提交额度用完就永久用完**。

**新模块把它做对了，老模块的 bug 还在。** 直接把 `feedbacks.js:47` 的写法抄到 `submissions.js:44` 即可（**S**，5 分钟）。
