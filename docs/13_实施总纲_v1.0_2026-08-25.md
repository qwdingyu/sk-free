## 0. 先读这一节：三个会造成事故的坑，已经排掉了

用户的要求是"千万不要方案有问题，造成重大事故"。审查过程中在**已有文档里**发现了 3 个会真造成事故的建议，全部已修正。列在最前面，因为如果有人拿着旧文档去执行，第一个坑就会踩上。

### 坑 1：🔴 `slug TEXT NOT NULL DEFAULT ''` + UNIQUE 索引 —— 生产库半迁移

`docs/11_docs08_09逐条审查报告` P1 建议、`docs/12_最终实施指南` §3.1 都写了：

```sql
ALTER TABLE sites ADD COLUMN slug TEXT NOT NULL DEFAULT '';   -- ❌
CREATE UNIQUE INDEX IF NOT EXISTS idx_sites_slug ON sites(slug);
```

并附注释"slug 允许 NULL 但设计意图要求非空，DEFAULT '' 已确保"。

**这段 SQL 一定会失败。** 实测：

```
$ sqlite3 t.db "ALTER TABLE sites ADD COLUMN slug TEXT NOT NULL DEFAULT '';"   → 成功
$ sqlite3 t.db "CREATE UNIQUE INDEX idx_slug ON sites(slug);"
Error: UNIQUE constraint failed: sites.slug
[exit code: 1]
```

原因：UNIQUE 索引把多个 `NULL` 视为互不相同（允许共存），但 `''` 是一个**具体值**，18 行全是 `''` 就是 18 个重复值。

**为什么这是"事故"而不是"小错"**：这条 CREATE INDEX 排在 12 条 `ALTER TABLE` 之后。在 `--remote` 生产 D1 上执行时，前 12 条已经生效，第 13 条失败。而 **SQLite 没有 `ADD COLUMN IF NOT EXISTS`**，重跑整个文件会立刻报 `duplicate column name: slug`。操作者会卡在一个不能前进也不能重跑的半迁移状态上——正是最难收拾的局面。

**正确写法**（本文 `0003_structured_quota_up.sql` 采用）：列可空 → 回填 `slug='s'||id` → 再建 UNIQUE 索引。实测通过。

### 坑 2：🔴 `needs_proxy INTEGER DEFAULT 0` —— DDL 违背了文档自己的原则

`docs/12` §3.4 写着"宁可留空也不要猜 `needs_proxy`"，但 §3.1 的 DDL 给了 `DEFAULT 0`。

`0` 的含义是"不需要魔法"。18 条里只有 2 条带"半DC"标签、其余 16 条**无从判断**。`DEFAULT 0` 会让这 16 条在前端显示"🔓 无需魔法"——而"无需魔法"是用户的关键决策依据。**这是在批量生产假信息**，和现在"100 积分显示成 100 刀"是同一类错误。

**正确写法**：`needs_proxy INTEGER`（可空，无默认值）。`NULL` = 未知，前端显示"未知"。

### 坑 3：🟠 "D1 ALTER TABLE 不可逆，新增列后无法删除" —— 事实错误，且后果是不敢回滚

`docs/12` §3.1 的这句警告会让操作者认为阶段 A 一旦执行就没有退路，从而在出问题时硬着头皮往前修。

实际上：SQLite 自 3.35（2021）起支持 `ALTER TABLE DROP COLUMN`；**而且无论什么版本，"建新表 → 拷数据 → 换名"的重建法都能回滚**。本文附带的 `0003_structured_quota_down.sql` 用的就是重建法，已在本机 **SQLite 3.32.2**（一个不支持 DROP COLUMN 的老版本）上实测通过：

```
DOWN 后: 列=16 站点=18 反馈=1 id最大=18
checkin 完好: 每日签到100积分（约60次API调用）
id 与 votes 关联完好: 16/3
```

顺带一个真实教训：**我第一版 DOWN 脚本用了 `DROP COLUMN`，在 3.32 上前面的 `DROP INDEX` 已经生效、后面 13 条 `DROP COLUMN` 全部语法错误**——留下"索引没了、列还在"的状态，比不回滚更糟。所以最终版改成表重建，不依赖版本。

> **执行前请先确认 D1 的版本**（本机无 Cloudflare 凭据，无法代查）：
> `cd worker && npx wrangler d1 execute SKFREE_DB --remote --command "SELECT sqlite_version();"`
> 无论结果如何，本文的 down 脚本都能用。

## 阶段 A：数据结构化（2~3 天）

### A.1 健康检查必须先修，再加 Cron

**顺序不能反。** 现在的链条是全自动、无确认、首页无痕迹的：

```
health.js:22  method:"HEAD"        →  超时
health.js:70  列入 newDeadUrls
index.js:528/558  前端自动 POST dead-urls/batch {action:"add"}
deadurls.js:74    UPDATE sites SET enabled = 0
sites.js:96       从 /api/sites filter 掉  →  首页消失
```

实测证据（18 个真实 URL，UA 与 `health.js:26` 一致）：17 个 HEAD 返回 200、0 次重定向；1 个失败：

```
https://agentrouter.org/register?aff=l1gl
  HEAD  →  code=000  t=5.008   （挂起后被对端断开）
  GET   →  code=200  t=2.484   ← 站点完全正常
  HEAD /（根域） →  code=200   ← 根域的 HEAD 是好的
```

**AgentRouter 是额度最高的两条之一（每日 25 刀）。管理员点一次「🧹 一键清理死链」，它就静默下线。** 把超时从 1500 改到 8000（`index.js:821-822`）治不了——它是 5 秒被断开，不是慢。

三个改动一起做、一起验：

| 改动 | 文件 | 内容 |
|---|---|---|
| HEAD 失败 fallback | `health.js:21-28` | HEAD 抛错或 ≥400 时，重试一次 `GET` + `Range: bytes=0-0`（只对失败 URL 触发，多 1 个 subrequest） |
| 放宽存活判定 | `health.js:31` | `403/405/429/501` 视为存活——能回状态码就说明服务器活着 |
| **移除自动下线** | `deadurls.js:74` + `index.js:528,558` | 改为 `health_fail_count` 连续 ≥3 次才停用；前端不再自动 `action:"add"`，改成列出结果由管理员勾选 |

**第三条是架构性的**：健康检查是概率性信号（网络抖动、限流、CF 挑战），把它直接接到不可逆动作上，本身就是错的。`0003` 已经预留了 `health_fail_count` 列。

> 修完这三条**之后**再加 `wrangler.toml` 的 `crons = ["0 */6 * * *"]`。顺序反了就是"定时下线站点"。

### A.3 关键设计决定与理由

| 决定 | 理由 |
|---|---|
| 所有新列**可空**，只有 `health_fail_count` 有 `NOT NULL DEFAULT 0` | 见坑 1、坑 2。"未知"必须能表达 |
| `slug = 's' \|\| id`，不从中文站名音译 | 18 条里 8 条中文名，音译规则不确定；一旦生成错误又建了 UNIQUE 索引，修正成本很高。可读性由管理员后续单独维护 |
| `quota_tier` 由**人工**判定，不自动折算 | 刀/元/积分/硬币/代币之间没有汇率。硬算就是现在"100 积分 → 100 刀"这类错误。机器存 min/max/unit 用于**显示**，人填 tier 用于**排序** |
| `quota_raw` 无条件保留 `checkin` 原文 | 任何结构化都不能丢原始信息 |
| `needs_proxy` 18 条**全部留 NULL** | 只有 2 条有"半DC"标签，其余无从判断。宁可显示"未知" |
| 新增 `kind` 字段 | 18 条里混了 4 种实体：14 个 API 站、2 个 TG 机器人、1 个号池（BOTCF）、1 个**域名工具（localhost.cc，根本不是 API 站）**。用同一套字段渲染必然大面积空白 |
| 反馈类型统一叫 `still_works` / `reported_dead` | `docs/09` 用 `dead`、`docs/12` 用 `dead`、本文统一为 `reported_dead`（避免与 `sites.dead` 语义混淆）。**以本文为准** |

### A.5 改名与删除的引用完整性

`feedbacks` 以 `site_name` 关联，但维护只做了一半：

| 操作 | `votes` | `dead_urls` | `feedbacks` |
|---|---|---|---|
| 改名（`sites.js:242-255`） | ✅ | 不需要 | ❌ **漏了** |
| 删除（`sites.js:296-300`） | ✅ | ✅ | ❌ **漏了** |

短期补两条语句：

```js
// 改名 batch 中追加
db.prepare("UPDATE feedbacks SET site_name = ? WHERE site_name = ?").bind(updated.name, siteName),
// 删除路径中追加
await dbRun(db, "DELETE FROM feedbacks WHERE site_name = ?", [siteName]);
```

**同时建议简化改名实现。** 现在是 `DELETE + INSERT`（`sites.js:243-246`），实测会换掉 `id`：

```
DELETE+INSERT:  id before=3  →  id after=19        ❌ id 漂移，还要手工搬 created_at
UPDATE:         id=16 slug=s16 created=… 全部保留   ✅ 且 UNIQUE 仍然拦重名
```

`name` 是 UNIQUE 但 `id` 才是主键，所以 `UPDATE sites SET name=?` 完全可行且更安全。长期按 `slug` 重指关联表，改名就不再牵动任何表。
