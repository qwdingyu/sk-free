## 一、部署规范（强制执行）

### ⚠️ 部署必须使用 `bash scripts/deploy.sh`

**禁止**直接运行 `npx wrangler deploy`。必须通过部署脚本：

```bash
# ✅ 正确
bash scripts/deploy.sh

# ❌ 禁止
npx wrangler deploy
cd worker && npx wrangler deploy
```

**原因**：`scripts/deploy.sh` 在部署前自动执行以下安全检查：

1. **模板字面量转义检查** — 对 `worker/index.js` 和 `worker/broadcast-html.js` 两个文件执行
   - 源码级扫描：检测模板字面量 `<script>` 块中的危险转义（`\n` → 应为 `\\n`）
   - 语法验证：提取 `<script>` 块用 `node --check` 验证 JS 语法
2. **任一检查失败则阻止部署**

### 部署后必须验证新构建真实生效

部署完成 ≠ 新代码在跑。验证三件套：

1. **API 行为验证**：用 curl 测试新增/修改的 API 端点
2. **HTML 内容验证**：`curl -s https://free.eforge.xyz/ | grep -c <关键标识>` 确认新功能存在
3. **D1 数据验证**：必要时用 `wrangler d1 execute` 确认数据已入库

### D1 Migration 部署

```bash
# 从 worker 目录执行（wrangler.toml 在此目录）
cd worker && npx wrangler d1 execute SKFREE_DB --remote --file=migrations/XXXX_xxx_up.sql --yes
```

## 二、用户反馈功能闭环审查

### 2.1 已实现的完整链路

```
用户点击「💬 反馈」→ 反馈模态框 → 选择类型 + 填写内容 → POST /api/feedback
    → D1 feedbacks 表（含 IP、速率限制、站点存在性校验）
    → Admin 后台「💬 用户反馈」tab → 列表/筛选/标记已读/已解决/删除
```

**数据流向**：公开页 → API → D1 → Admin 面板 ✅

### 2.2 存在的闭环缺口

| 缺口 | 严重度 | 说明 |
|------|--------|------|
| 反馈无通知机制 | 中 | Admin 不知道有新反馈，必须主动打开 tab 查看。建议在 header 的"站点管理"旁显示未读反馈数 |
| 反馈无站点关联跳转 | 低 | Admin 看到反馈后无法一键跳到对应站点编辑页面。建议反馈卡片加"编辑站点"按钮 |
| 无"还能用/已失效"快捷反馈 | 中 | docs/09 提出的最低摩擦鲜度入口，当前反馈需要选类型+填内容，门槛偏高 |
| 前端防重复纯客户端 | 低 | localStorage 清空即可重复反馈，后端只有 IP 限流（10次/天） |

### 2.3 docs/08 指出的线上问题（已修复）

docs/08 声称"线上反馈功能是死的"（`grep -c feedbackModal → 0`），原因是 `broadcast-html.js` 缺少反馈 JS 代码。

**本次部署已修复**：我已将反馈 HTML、CSS、JS 全部同步到 `broadcast-html.js`，部署后验证 `grep -c feedbackModal → 5`。

**但根因未消除**：`broadcast/` 目录和 `worker/broadcast-html.js` 仍是手工双副本，下次新增前端功能仍可能丢失。docs/09 提出的 `scripts/build-html.js` 自动构建方案应尽快实施。

## 四、docs/09 审查意见

### 4.1 方案质量：优秀

这是我在同类项目中见过的**最好的前端重构方案之一**：

| 亮点 | 说明 |
|------|------|
| 诊断链清晰 | 从数据模型 → 前端表现 → 用户体验，因果链完整 |
| 优先级正确 | "先改数据模型，再改前端"——70% 问题在数据层的判断准确 |
| 验收标准可测 | 12 条量化指标，不是形容词 |
| 明确不做的事 | 6 条"不做"清单，有效防止范围蔓延 |
| 附录可直接执行 | 18 条数据的迁移映射表、单位显示映射、新数据契约 |

### 4.2 需要补充/修正的地方

| 项 | 问题 | 建议 |
|----|------|------|
| 阶段 0 未提及 deploy.sh 检查范围 | 文档指出 `broadcast-html.js` 未被检查，但未给出修复方案 | 已在本次部署中修复（deploy.sh 现在检查两个文件） |
| `quota_tier` 人工判定 | 方案说"18 条数据 5 分钟填完"——这是乐观估计 | 实际需要逐条核对原始数据、确认单位和周期，建议预留 30 分钟 |
| "删除 loadVotes()" | 方案说 `/api/sites` 已返回 votes | 需先验证 `handleGetEnabledSites` 是否真的返回了 `votes` 字段，否则删除后投票数据会丢失 |
| 无回滚方案 | 10 天重构计划没有回滚策略 | 建议每阶段结束后打 tag，确保可回退 |
| 表格视图的移动端适配 | 方案说"保留4列"但未给出具体列宽 | 移动端表格易出现横向滚动，建议补充断点策略 |

### 4.3 我的专业建议

**1. 分阶段实施时，阶段 0 应包含反馈闭环补全**

docs/09 的阶段 0 是"止血"，但只提了 build 脚本和额度误报。建议加入：

- 反馈卡片加"编辑站点"按钮（Admin 侧）
- header 显示未读反馈数
- 这两个改动各 30 分钟，但对闭环完整性至关重要

**2. "还能用/已失效"一键反馈应提前到阶段 0**

这是 docs/09 阶段 D 的内容，但它是**成本最低、价值最高的鲜度入口**。实现方式极简：

- 公开页卡片加两个按钮："👍 还能用" / "💀 已失效"
- 复用现有 `/api/feedback`，`type` 加 `still_works` / `dead`
- 无需填文本，一键提交

这个改动 1 小时内可完成，但能让社区参与鲜度维护。

**3. 不要跳过阶段 A 直接做阶段 B**

docs/09 已经明确说了"跳过 A 直接做 B 是无效劳动"。务必严格遵守这个顺序。

**4. `needs_proxy` 字段应由管理员逐条确认，不要猜**

docs/09 附录中 `needs_proxy` 列标注了"需人工确认"。错误的 `needs_proxy` 值会直接误导用户（"无需魔法"标签是关键决策因素）。宁可显示"未知"也不要猜。
