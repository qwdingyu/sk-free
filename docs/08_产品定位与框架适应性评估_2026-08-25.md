# 08 产品定位与框架适应性评估

> 日期：2026-08-25
> 评估对象：sk-free（free.eforge.xyz）—— Worker + D1 + 内嵌前端
> 评估方式：全量代码精读 + 线上接口实测（`/api/sites`、`/api/schema`、`/` HTML）
> 结论提要：**通用化方向应当收回；当前的通用化是负收益，并已造成线上功能丢失。产品真正缺的不是"通用框架"，是"数据结构化"和"可信度"。**

---

## 0. 先说三个实测事实

这三个数字决定了后面所有判断，请先看它们。

**事实一：线上只有 18 条数据。**

```
curl -s https://free.eforge.xyz/api/sites | jq '.sites|length'
→ 18
```

为这 18 条建了：D1 六张表、KV 两个 key、29 个路由、schema 配置引擎、5 套模板、健康检查、死链名单、投票、反馈、审核队列、Admin 后台（`worker/index.js` 内嵌 640 行 HTML）。代码 9,551 行。**代码行数 / 数据条数 = 530 : 1。**

**事实二：核心字段大面积为空。**

| 字段 | 有值条数 | 填充率 |
|---|---|---|
| `name` / `url` / `tags` / `summary` | 18 | 100% |
| `checkin`（签到额度） | 14 | 78% |
| `notes` | 9 | 50% |
| `rate`（倍率） | 7 | 39% |
| `register`（注册方式） | 3 | **17%** |
| `models`（支持模型） | 2 | **11%** |

而前端卡片固定渲染 4 行事实（`broadcast/app.js:535-538`：签到/模型/注册/倍率）。也就是说**每张卡片平均有 2.6 行是空的**，卡片高度参差、信息密度极低。用户说"前端太粗、平铺没威力"——根因在这里，不在 CSS。

**事实三：线上页面的反馈功能曾经是死的——而且是"静悄悄"死的。**

本次审计开始时（2026-08-25 21:2x）实测：

```
curl -s https://free.eforge.xyz/ | grep -c feedbackModal
→ 0
```

> **更新（同日 21:34~21:46）**：`worker/broadcast-html.js` 已被手工补齐，线上 `grep -c initFeedbackForm` 现为 2，反馈功能已恢复；`scripts/deploy.sh` 也已扩展为同时检查 `index.js` 和 `broadcast-html.js` 两个文件。
>
> **但根因一个都没消除**：修复方式是人再一次手工把 161 行 JS 复制进那个 2237 行的单字符串。转义检查只能验证"语法没坏"，**验证不了"内容有没有漏"**。下一次前端改动仍然会漏，而且仍然不会有任何信号。这恰好证明了下面这段分析——所以本节内容原样保留。

后端有 `POST /api/feedback`（`worker/index.js:902`）、有 `feedbacks` 表（`0002_add_feedbacks_up.sql`）、Admin 有反馈管理面板（`worker/index.js:829`）。前端 `broadcast/app.js:744-903` 写了 161 行完整反馈逻辑。**但用户永远点不到它。**

原因是前端存在三份不同步的副本：

| 副本 | 反馈 CSS | 反馈弹窗 HTML | 反馈 JS 逻辑 | 反馈入口按钮 |
|---|---|---|---|---|
| `broadcast/`（静态源） | ✅ | ✅ | ✅ | ✅ |
| `worker/broadcast-html.js`（内嵌，2237 行单字符串） | ✅ | ✅ | ❌ | ❌ |
| **线上实际** | ❌ | ❌ | ❌ | ❌ |

`worker/index.js:696` 返回的是 `broadcast-html.js`，静态目录 `broadcast/` 早已不是线上来源。逐行 diff 显示：`styles.css` 100% 被复制进内嵌版，`index.html` 96%，`app.js` 只有 79.5%——**缺的 20% 正好是整个反馈系统**。

> 这就是"通用化框架"的真实代价：为了让 Worker 能独立部署一份 HTML，前端被手工复制成两份；一次功能开发（反馈）在复制环节丢了一半，没人发现，因为没有构建、没有校验、没有测试。

## 1. 行业视角：这个产品到底在什么赛道

### 1.1 它不是"导航站"

`README.md:3` 自称"静态 GitHub Pages 导航站"。但看数据就知道不是。

真正的导航站（如 hao123、各类 AI 工具导航）卖的是**收录广度**，价值随条目数增长，条目一旦收录基本不变。而这里 18 条数据的实际内容是：

```
AgentRouter   checkin='每日 25 刀（需要登出再登录）'  register='GitHub'
AnyRouter     checkin='每日登录 25 刀'                register='Linux.do'
哈基米API站    checkin='每日签到10-20元'               rate='1（基础价格超高）'
斑马API        checkin='每日签到100积分（约60次API调用）'
星见雅API      checkin='50-100代币'
Cavoti API    checkin='绑定X和Google免费'
```

这些不是"网址"，是**羊毛情报**：额度多少、怎么领、有什么坑、今天还有没有。它的价值 100% 绑定**时效性**和**可信度**，而不是收录数量。

### 1.2 它在的赛道：时效性情报聚合（羊毛/白嫖情报站）

这个赛道的竞品是 Linux.do 的帖子、TG 频道、GitHub 上的 awesome-free-api 列表。它们的共同痛点，恰好就是这个产品的机会窗口：

| 竞品形态 | 痛点 |
|---|---|
| 论坛帖 / TG 频道 | 信息流式，昨天的额度信息和今天的混在一起，无法比较；找一个"今天还能签到 25 刀"的站要翻 20 条消息 |
| GitHub awesome 列表 | 半年不更新，一半链接已死；PR 门槛高，普通用户不会提 |
| 各家自建站 | 只有自己的站，没有横向对比 |

**这个赛道的护城河只有两样东西：**

1. **鲜度** —— 用户敢信"这条今天还有效"
2. **可比性** —— 用户能一眼横向比较"哪个额度大、哪个不用魔法"

**这两样这个产品目前都不具备**，下面逐条说。

### 1.3 鲜度：完全缺失

- 前端不显示任何时间。数据里有 `updatedAt`（`worker/src/sites.js:34` 返回了），前端 `app.js` 从头到尾没用过。
- 前端不显示健康状态。后端 `handleGetEnabledSites`（`worker/src/sites.js:96`）会把死链**直接过滤掉**——用户看不到"这站挂了"，只会觉得"你收录得好少"。信息被丢弃而不是被呈现。
- 健康检查只有手动触发（`worker/src/health.js`，无 Cron Trigger）。没人点，就永远不检查。
- `app.js:279-311` 写了 `todayInShanghai()` / `extractDescriptionDates()` / `isCurrentDatedSite()` 三个函数，明显是想做"日期时效判断"的——**定义了，从未调用**。33 行死代码。这说明"鲜度"这件事被想到过，但没做完。

### 1.4 可比性：被数据模型堵死

用户最想问的问题是"**哪个签到额度最大**"。当前答不了，因为 `checkin` 是自由文本，18 条有 **11 种不同写法**：

| 原始值 | 数值 | 单位 | 周期 |
|---|---|---|---|
| `0.5` | 0.5 | ?（默认刀） | ? |
| `每日 25 刀（需要登出再登录）` | 25 | 刀 | 每日 |
| `每日登录 25 刀` | 25 | 刀 | 每日 |
| `每日签到2刀` | 2 | 刀 | 每日 |
| `0.5-1刀` | 0.5~1 | 刀 | ? |
| `签到1-5积分` | 1~5 | 积分 | 每日 |
| `每天1-3硬币` | 1~3 | 硬币 | 每日 |
| `每日签到10-20元` | 10~20 | 元 | 每日 |
| `每日签到100积分（约60次API调用）` | 100 | 积分 | 每日 |
| `50-100代币` | 50~100 | 代币 | ? |
| `绑定X和Google免费` | — | — | 一次性 |
| `限免` | — | — | — |

前端只好用正则硬猜（`app.js:497` `site.checkin.match(/\d+(\.\d+)?/g)` 取最大值），然后一律加上"刀"字（`app.js:518` `badge.textContent = ${label} 刀`）。**结果："斑马API 每日签到 100 积分"在页面上显示成 `100 刀` 的高额度徽章，"公益Plus 签到1-5积分"显示成 `5 刀`。这是在向用户输出错误信息。**

> 这是全项目最该马上修的问题：它不是体验瑕疵，是内容错误。详见 `docs/09`。

### 1.5 筛选维度：数学上就是无效的

`app.js:12` 硬编码了优先标签：

```js
const PRIORITY_TAGS = ["全部", "签到", "生图", "DC系", "半DC", "非DC", "抽奖"];
```

对照 18 条数据的真实标签分布：

| 标签 | 命中 | 占比 | 作为筛选器的判别力 |
|---|---|---|---|
| 非DC | 15 | **83%** | 几乎为零（筛完还剩 15/18） |
| 签到 | 12 | 67% | 弱 |
| 生图 | 8 | 44% | 可用 |
| 限免 | 6 | 33% | 可用 |
| 账号 | 2 | 11% | — |
| 半DC | 2 | 11% | — |
| 按次 / 域名 | 1 | 6% | — |
| **DC系** | **0** | **0%** | **空按钮** |
| **抽奖** | **0** | **0%** | **空按钮** |

再叠加两个设计缺陷：

- **单选**：`state.activeTag` 是单值（`app.js:29`），无法"签到 + 生图"交叉筛选。
- **一次筛完就没了**：18 条数据 + 单选筛选 = 大部分点击后仍是 8~15 张卡片平铺，用户没获得任何决策帮助。

同时，`/api/schema` 里 `tags.options` 只有 7 个（`签到/生图/DC系/半DC/非DC/限免/抽奖`），而实际数据里出现了 `账号`、`按次`、`域名` 三个 schema 里没有的标签。**schema 对数据没有约束力**——这直接引出下一章。

## 2. 上帝视角：框架的适应性、扩展性、通用性

### 2.1 结论先行：评分表

| 维度 | 评分 | 一句话理由 |
|---|---|---|
| **适应性**（换个行业能用吗） | ⭐☆☆☆☆ | D1 表列是固定 DDL，schema 里加一个字段存不进去 |
| **扩展性**（加功能容易吗） | ⭐⭐☆☆☆ | 后端模块化尚可；前端是 2237 行单字符串 + 手工复制，改一次丢一半功能 |
| **通用性**（是真引擎还是配置文件） | ⭐☆☆☆☆ | schema 只驱动了 Admin 的一个 JSON 编辑框，不驱动存储、不驱动校验、不驱动前端 |
| **可运维性** | ⭐⭐☆☆☆ | 无构建、无测试、无 CI 校验、无 Cron、单 ADMIN_TOKEN |
| **单品完成度**（作为羊毛情报站） | ⭐⭐☆☆☆ | 数据能进能出能投票，但没鲜度、没可比性、反馈链路线上是死的 |

### 2.2 "Schema 引擎"是伪配置——三层证据

`docs/06_通用信息收集平台方案` 声称"渲染引擎 schema→HTML 动态生成"、"10 分钟上线同类站点"、阶段一二三"已完成"。实测**引擎层一行都没有**。

**证据一：存储层写死在 DDL 里。**

`worker/migrations/0001_init.sql:14-30`：

```sql
CREATE TABLE IF NOT EXISTS sites (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL UNIQUE,
  url TEXT NOT NULL DEFAULT '',
  original_url TEXT ..., ref TEXT ..., tags TEXT ..., summary TEXT ...,
  enabled INTEGER ..., checkin TEXT ..., models TEXT ..., rate TEXT ...,
  register TEXT ..., notes TEXT ..., sort_order INTEGER ..., created_at ..., updated_at ...
);
```

`checkin` / `models` / `rate` / `register` 是**物理列**。用 `templates/roster/schema.json` 时它要的 `avatar`、`links` 字段**没有列可以存**；`catalog` 要的 `price`、`features` 也没有。切模板 = 写 migration 改 DDL。

**证据二：读写层写死在 JS 里。**

`worker/src/sites.js:18-35` `formatSiteRow()` 逐字段手写 15 行映射。`sites.js:418-543` 的导入逻辑同样逐字段硬编码。schema 加一个字段，这两处都要改。

**证据三：前端 0 消费 schema。**

`broadcast/app.js` 全文 918 行，**没有任何一次 `fetch("/api/schema")`**。而 schema 里明明配了显示规则：

```json
"display": { "layout": "grid", "columns": 3, "sortBy": "default",
             "priorityTags": ["全部","签到","生图","限免"] },
"theme":   { "primary": "#087f78", "accent": "#b8e35a" }
```

对照前端实际：`columns:3` → 硬编码在 `styles.css:781` `grid-template-columns: repeat(3, minmax(0,1fr))`；`priorityTags` → 硬编码在 `app.js:12`（且内容还不一样，多了 DC系/半DC/非DC/抽奖）；`theme.primary` → 硬编码在 `styles.css:11` `--teal: #087f78`。

**schema 是一份写在 KV 里、和真实行为长得很像但毫无因果关系的注释。**

### 2.3 五套模板是同一个模板换名字

| 字段 | collection | roster | catalog | directory | feedback |
|---|---|---|---|---|---|
| name / url / tags / summary | ✅ | ✅ | ✅ | ✅ | ✅ |
| 独有字段 | `date` | `avatar` `links` | `price` `features` `rating` | `rating` | `priority` |

共同骨架 `name + url + tags + summary` 占 100%，差异只有 1~2 个字段，而且**没有一个字段是当前 DDL 存得下的**。

更关键的是：这 5 套模板绕开了通用化真正的难点。做通用信息平台，难的从来不是"字段列表"，而是：

- **多值与关系**：一个条目属于多个分类、条目之间有引用
- **排序语义**：`price` 该按数值排还是字符串排？`rating` 的满分是多少？
- **视图差异**：roster（人员名册）要头像网格，catalog（商品目录）要价格对比表，feedback（反馈表）要状态流转看板——**这三个的界面完全不同，靠 `layout: "grid"` 一个字段是描述不出来的**
- **权限**：feedback 模板的提交者不该看到别人的反馈；roster 可能需要登录

`templates/*/schema.json` 一个都没碰。

### 2.4 `scripts/init.sh` 自动化了什么

读一遍 48 行就知道（`scripts/init.sh:39-41`）：

```bash
mkdir -p "$PROJECT_DIR"
cp "$TEMPLATE_DIR/schema.json" "$PROJECT_DIR/schema.json"
```

**它只做了一次 `cp`。** 然后打印"下一步：编辑 schema / 部署 Worker / 通过 Admin 导入 Schema / 导入初始数据"——四步全是手工。而且如前所述，"导入 Schema"之后数据依然存不进去。

所谓"10 分钟上线"，实际是：改 DDL + 写 migration + 改 `formatSiteRow` + 改导入导出 + 改前端渲染 + 改内嵌 HTML 副本 + 创建 D1/KV + 部署。**实测工作量 1~2 天，且第二份前端副本大概率再丢功能一次。**

### 2.5 多租户能力为 0

所有表都没有 `tenant_id` / `project_id`。一个 Worker 部署 = 一个数据集。第二个站点必须是完整的第二套 Worker + D1 + KV + 域名。这意味着"通用化"带来的不是复用，而是**副本数量翻倍的维护成本**。

### 2.6 通用化的投入产出账

| 项 | 数量 |
|---|---|
| 为通用化写的代码 | `schema.js` 65 行 + Admin schema 面板 ~80 行 + `init.sh` 48 行 + 5 套 template ~180 行 + `check-template-escapes.js` 160 行 ≈ **530 行** |
| 由通用化产生的额外维护面 | 前端第二份副本 **2237 行**（`broadcast-html.js`） |
| 由此已经造成的线上故障 | **1 个功能整体丢失**（反馈系统，161 行 JS 未被复制） |
| 收益：实际跑起来的第二个实例 | **0 个** |

**净收益为负。** 这不是"技术债"，这是"为一个没有需求的场景付了首付并且每月还在还利息"。

## 3. 用户视角：一次真实的使用旅程

假设用户 A 在 TG 群看到有人推荐这个站，点进来，他的目标是：**找一个今天还能免费用、额度够跑几十次 Claude 请求的 API 站**。

| 步骤 | 他遇到什么 | 问题 |
|---|---|---|
| 1. 打开页面 | 白屏一段时间（`app.js:663` 先 `await loadJson()` 再 `await loadVotes()` **串行两次请求**，无骨架屏） | 首屏慢且空 |
| 2. 看首屏 | Hero 占满一屏（`styles.css:140` `min-height:180px` + padding），下面是 3 个统计数字"收录 18 / 可签到 12 / 可生图 8" | 统计数字对他的决策毫无帮助；而且这三个数字是**筛选后**的（`app.js:353` `filteredSites()`），一搜索就变，语义混乱 |
| 3. 想筛选 | 一排标签按钮，点"非DC"→ 还剩 15 条；点"DC系"→ 0 条空结果；不能同时选"签到+生图" | 筛选器没帮他缩小范围 |
| 4. 比较额度 | 卡片上有 `100 刀` `25 刀` `5 刀` 徽章 | **`100 刀` 实际是 100 积分（斑马API）**，他按这个排序会选错 |
| 5. 想排序 | 只有"默认排序"和"按评分排序"（`app.js:13-16`） | 18 条数据全部 `votes: {up:0, down:0}`，**"按评分排序"等于不排序** |
| 6. 判断是否还活着 | 页面没有任何时间信息、没有健康状态 | 他不敢信，回 TG 问人 |
| 7. 发现某站挂了想反馈 | **没有反馈按钮**（线上 0 处） | 情报无法回流，站点继续挂着 |
| 8. 想分享筛选结果给朋友 | URL 永远是 `https://free.eforge.xyz/`，无 query 同步 | 只能截图 |

**8 步里 7 步不及格。而其中 6 个问题的根因不在 CSS 或布局，在数据模型和信息架构。**

### 3.1 交互层的具体硬伤（可逐条修）

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| 1 | 9 处 `alert()` 做错误提示 | `app.js:167,169,172,732,735,842,846,868,871` | 阻塞式弹窗，移动端体验极差；页面已有 toast 组件（`app.js:883`）却不用 |
| 2 | 搜索无防抖，每次按键全量重绘 | `app.js:909-912` → `render()` → `renderFilters()` 重建所有按钮 | 输入时标签按钮整排被 `replaceChildren` 重建，排序下拉框状态被重置 |
| 3 | 重复请求投票数据 | `/api/sites` 已在每条数据内返回 `votes`（`sites.js:99`），`app.js:74` 又请求一次 `/api/votes` | 多一个 RTT，且两份 votes 数据可能不一致 |
| 4 | `filteredSites()` 每次渲染算 2 遍 | `app.js:353` + `app.js:590` | 小数据量无感，但说明渲染管线没设计 |
| 5 | `state.metadata` 是死代码 | `app.js:666` 读 `data.metadata`，但公开接口 `handleGetEnabledSites`（`sites.js:93-101`）**不返回 metadata** | 永远是 `{}` |
| 6 | 33 行日期时效代码从未调用 | `app.js:279-311` | 想做鲜度但没做完 |
| 7 | 投票/反馈防重复纯客户端 | `app.js:94` localStorage `sk-free-votes` | 清 localStorage 或换隐私窗口即可重复投；后端 IP 限流是 10 次/小时（`votes.js:11`），刷票门槛极低 |
| 8 | 投票主键是站点名 | `votes.site_name` 是 PRIMARY KEY（`0001_init.sql`） | **站点改名 = 票数归零、历史断裂**；`dead_urls` 按 url、`submissions` 按 `site_name`，同理 |
| 9 | 无 URL 状态、无键盘导航、无 `aria-live` | 全文无 `history.pushState`、无 `aria-live` | 不可分享、不可访问 |
| 10 | 提交表单是静态 HTML 写死 7 个字段 | `index.html:122-149` | 与 `schema.submit.fields` 无关；schema 改了表单不动 |

### 3.2 一个隐藏的数据 bug

`worker/src/submissions.js:42-46`：

```js
const ipSubmissions = await dbAll(db,
  "SELECT id FROM submissions WHERE ip = ? AND created_at > ?",
  [ip, (now - SUBMIT_RATE_WINDOW_MS).toString()]);
```

`created_at` 由 `datetime('now')` 写入，格式是 `"2026-08-25 00:40:40"`；这里用 epoch 毫秒字符串 `"1756000000000"` 去比较。SQLite 做字符串比较：`"2"` > `"1"`，**恒为真**。结果是滑动窗口失效——每个 IP 的 5 次提交额度**用完就永久用完，24 小时后不恢复**。同一条 `submissions.js:118` 的 `new Date("2026-08-25 00:40:40")` 在 Safari 上会得到 `NaN`。

## 4. 建议：收回通用化，单品做深

### 4.1 战略判断

**停止投资"通用信息收集平台"。** 判断依据不是"通用化不好"，而是三个具体条件都不满足：

| 做通用框架的前提条件 | 当前状况 |
|---|---|
| 有 ≥3 个真实待建实例，且需求已明确 | 0 个 |
| 单品已经跑通、有稳定用户和留存 | 18 条数据，投票全 0，无留存数据 |
| 团队有余力承担双份维护成本 | 已经因为双份前端丢了一个功能 |

**同时不要删除 templates/ 和 schema.js。** 它们是有价值的设计资产，只是不该被当成运行时引擎。处理方式见 4.4。

### 4.2 重新定位：从"导航站"到"可信度账本"

一句话定位：

> **每天更新的免费 API 额度对比表——每条都标注最后验证时间和社区反馈，让你 30 秒选出今天能用的那个。**

对比现在的自我描述（`index.html:83`"收录可注册、可签到、可生图和长期备用的 API 站点"）：删掉了"收录"这个数量叙事，换成"对比 + 验证时间"这个可信度叙事。

三条不可让的产品原则：

1. **鲜度必须可见。** 每条数据必须显示"最后验证时间"。没验证过的条目要显式标注"未验证"，而不是混在里面装作可用。
2. **可比的必须结构化。** 额度、周期、单位、是否需要魔法——这些是用来筛选和排序的，必须是结构化字段，不能是自由文本。
3. **死链要展示而不是隐藏。** 当前 `sites.js:96` 把死链过滤掉了。应该改成标记为"已失效"并放到列表末尾/折叠区——"我们知道它挂了"本身就是可信度。

### 4.3 分阶段路线（按 ROI 排序）

**阶段 0：止血（0.5 天，必须先做）**

| 任务 | 具体动作 | 验收 |
|---|---|---|
| 消灭前端双副本 | 写 `scripts/build-html.js`：读 `broadcast/{index.html,styles.css,app.js}` → 内联拼装 → 生成 `worker/broadcast-html.js`。加入 `deploy.sh` 前置步骤 | `git diff` 后 `broadcast-html.js` 由脚本生成，人工不再编辑 |
| ~~恢复反馈功能~~ | 已于 21:34 手工修复（线上 `grep -c initFeedbackForm` = 2）。**注意：手工修复不算完成**——上一步的构建脚本才是防止再次发生的措施 | 生成结果与 `broadcast/` 源逐行一致 |
| 修签到额度误报 | `app.js:518` 停止无脑加"刀"，改为回显原文单位（临时方案，阶段 1 做结构化） | `斑马API` 不再显示 `100 刀` |
| 修提交限流 bug | `submissions.js:44` 改 `created_at > datetime('now','-1 day')` | 24 小时后额度恢复 |

**阶段 1：数据结构化（2~3 天，价值最大）**

这是解锁前端一切能力的前提。核心是把 `checkin` 拆成可计算字段，并引入稳定主键和鲜度字段。

| 任务 | 具体动作 |
|---|---|
| 稳定主键 | `sites` 增 `slug TEXT UNIQUE`；`votes` / `dead_urls` / `feedbacks` 改用 `site_id` 或 `slug` 外键。**改名不再丢票** |
| 额度结构化 | 新增 `quota_amount REAL`、`quota_amount_max REAL`、`quota_unit TEXT`、`quota_period TEXT`（daily/once/none）、`quota_raw TEXT`（保留原文不丢信息） |
| 鲜度字段 | 新增 `verified_at TEXT`、`verified_by TEXT`（admin/health-check/community） |
| 二值化关键属性 | `needs_proxy INTEGER`（替代语义模糊的 DC系/半DC/非DC）、`supports_image INTEGER` |
| 标签治理 | 用 schema 的 `tags.options` 做真实校验；把 0 命中的 `DC系`/`抽奖` 从优先标签里删掉，把实际存在的 `账号`/`按次`/`域名` 纳入 |
| 定时健康检查 | `wrangler.toml` 加 Cron Trigger（每 6 小时），自动写 `verified_at` |

18 条数据的 `checkin` → 结构化映射表已在 `docs/09` 附录给出，可直接执行。

**阶段 2：前端重构（3~4 天）**

详见 `docs/09_前端信息架构与交互重构方案_2026-08-25.md`。核心四件事：默认表格/排行榜视图、多维筛选 + URL 同步、卡片信息分层、鲜度与可信度可视化。

**阶段 3：可信度闭环（2 天）**

| 任务 | 说明 |
|---|---|
| "还能用 / 已失效"一键反馈 | 复用现有 `/api/feedback`，`type` 增加 `still_works` / `dead`。这是社区维护鲜度的最低摩擦入口 |
| 反馈驱动 `verified_at` | N 个 `still_works` 自动刷新验证时间；M 个 `dead` 自动进死链候选待管理员确认 |
| 投票防刷 | 改为 IP + UA 哈希做服务端幂等键（`votes.js` 已有 `rate_limits` 表可复用），localStorage 只做 UI 状态 |
| 变更历史 | `site_history` 表记录额度变化，前端显示"额度从 25 降到 10"——这是竞品做不到的差异化 |

### 4.4 templates/ 和 schema 的正确定位

不要删，但要改变契约：

- `templates/*/schema.json` → 降级为 **`docs/templates/` 下的设计草案**，明确标注"设计参考，非运行时配置"。
- `worker/src/schema.js` 的 `DEFAULT_SCHEMA` → 升级为**唯一的字段真相源**，但要真正接线：
  - 后端校验读它（现在只在 `index.js:862` 做了类型白名单校验）
  - Admin 表单读它生成输入框
  - 前端提交表单读它生成字段（`index.html:122-149` 现在是写死的）
  - 前端展示读它的 `label` 和 `display`
  这叫"一处定义、多处消费"，是**单品内部的收敛**，不是跨行业的通用化。做到这一步，未来真要做第二个实例时，通用化的地基已经在了。
- `scripts/init.sh` → 明确改名为 `scripts/scaffold-schema.sh` 并在输出里说明"仅生成 schema 草案，不含 DDL 与前端适配"，避免误导。

### 4.5 什么时候可以重启通用化

给一个明确的触发条件，避免以后再凭感觉走回头路：

> **当出现第 2 个真实要上线的实例，且它与 sk-free 的差异可以完全由"字段列表 + 展示配置"描述（不需要新的视图形态、不需要权限模型、不需要条目间关系）时**，才把 schema 引擎做实。

做实的最小路径也已经清楚：`sites` 表加一列 `extra JSON`，schema 里 `fields` 未在物理列中的字段全部落到 `extra`，`formatSiteRow` 改为按 schema 遍历。这一步大约 200 行，但**在没有第二个实例前不要做**。

## 5. 一页总结

| 问题 | 真实根因 | 该改哪里 |
|---|---|---|
| "前端太粗、平铺没威力" | 数据字段填充率 11%~78% + 额度是自由文本无法比较 + 筛选维度 83% 命中率 | **先改数据模型**（阶段 1），再改前端（阶段 2） |
| "框架不通用" | D1 是固定 DDL，schema 不驱动存储/校验/前端；templates 是同一骨架换名 | **不要修通用化，收回它**；把 schema 收敛为单品内部的字段真相源 |
| 反馈功能线上失效（已手工修复，根因仍在） | 前端手工复制成两份，20% 代码没复制过去；转义检查验证不了内容缺失 | **写构建脚本消灭副本**（阶段 0，半天） |
| 用户不敢信数据 | 无鲜度展示、死链被隐藏、健康检查无 Cron、无反馈入口 | 阶段 1 + 阶段 3 |
| 过度工程 | 530:1 的代码/数据比；为 0 个第二实例付了双份维护成本 | 停止新增抽象层，把力气花在 18 条数据的质量上 |

**最重要的一句话**：这个产品现在的瓶颈不是"框架不够通用"，而是"18 条数据没有一条能让用户放心地点进去"。把这 18 条做成全网最准最新的免费 API 额度对比表，比支持 5 套模板有价值一百倍。

## 附录 A：后端工程债务（每条已逐行核验）

补充审计，与前面的产品结论独立。**每条都读过代码确认，并标注了实际严重度**——不要按"听起来严重"排序。

### A.1 高：批量操作是串行 N+1，会直接撞 Workers 平台限制

`worker/src/sites.js:362-384`（批量加/减标签）：

```js
for (const name of names) {
  const row = await dbGet(db, "SELECT tags FROM sites WHERE name = ?", [name]);   // 查
  ...
  await dbRun(db, "UPDATE sites SET tags = ? ... WHERE name = ?", [...]);          // 写
}
```

**每个站点 2 次串行 D1 往返。** `worker/src/deadurls.js:63-84` 的 `batchDeadUrls` 同样是每 url 2 次串行（INSERT/DELETE + 联动 `UPDATE sites`）。

后果不只是慢：**D1 查询计入 subrequest 配额**。最近提交的"一键清除全部死链"（`ab034f1`）在死链较多时会先撞上限报 1101，而不是慢慢跑完。

修法很便宜（**S**）：`dbBatch` 已在 `worker/src/db.js:60` 实现，而且**已经 import 进 sites.js 了**（`sites.js:6`），只是这两处循环没用它。改成一次 `SELECT ... WHERE name IN (?,?,…)` 取全部行 → 内存里算好新 tags → 一次 `db.batch([...])` 提交。

### A.2 中：健康检查的 subrequest 余量算错了

`worker/src/health.js:63` 注释写"≤48 个 fetch = ≤49 subreq，安全在 50 限制内"，漏算了后续 D1 写入：

| 消耗项 | 数量 |
|---|---|
| `getDeadUrls` 读取（`health.js:56`） | 1 |
| 并发 fetch（`health.js:63` `urls.slice(0, 48)`） | 48 |
| 发现新死链后的写入（每条 INSERT + 联动 UPDATE sites） | **2 × N** |

48 + 1 = 49 已经贴着 50，只要有 1 条新死链就超。目前没炸是因为前端只发 45 条一批（`worker/index.js:521` `BATCH_SIZE = 45`）——**代码里的 48 和实际调用的 45 是两个不一致的常量，靠前端的保守值兜住了后端算错的余量**。

修法（**S**）：上限统一到一处常量并降到 40，死链写入改一次 `db.batch()`。长期（**M**）：换 Cron Trigger 分批跑，见正文阶段 1。

### A.3 中：管理 API 限流是进程内存 Map，实际约束不住

`worker/src/utils.js:75` `const adminRateMap = new Map()`。Workers 的 isolate 按 colo 分布且随时回收：

- 换一个 colo（或 isolate 被回收）→ 计数从 0 开始；注释自己也写了"Worker 单实例，重启清空"（`utils.js:74`）
- `CF-Connecting-IP` 取不到时 fallback 为字符串 `"unknown"`（`utils.js:98`）→ **所有取不到 IP 的请求共享同一个计数桶**，互相把对方限流掉

修法（**S**）：`rate_limits` 表已存在（`0001_init.sql`），复用它；或 KV + TTL。

### A.4 中：`/admin` 页面无服务端鉴权

`worker/index.js:708-710` 直接返回 HTML，无任何校验；token 存 localStorage，由前端 JS 附到 `Authorization` 头。

**风险要说准**：所有写操作都被 `/api/admin/*` 上的 `requireAuth`（`utils.js:60-67`）挡住了，所以这不是"后台裸奔"。真实影响是：① 整个后台 UI 结构、字段、接口路径对外公开，等于送出一份 API 文档；② token 在 localStorage，任何 XSS 都能取走，且**单 token 无法吊销、无过期、无操作日志**。

修法（**S~M**）：`/admin` 加一层最小校验（Basic Auth 或预共享 `?k=`），token 改 HttpOnly Cookie 并加 `token_version` 以便吊销。RBAC 在单人维护的项目上**不值得做**。

### A.5 低：CORS 反射任意 Origin —— 这是有意设计，不是漏洞

`worker/src/utils.js:16`：`"Access-Control-Allow-Origin": request.headers.get("Origin") || "*"`。

看着危险，实际不是：**没有 `Allow-Credentials`，也没有 Cookie 会话**，鉴权纯靠 `Authorization` 头，浏览器不会自动带任何凭证，第三方站点只能读到本来就公开的 `/api/sites`。`utils.js:8-10` 的注释已解释这个取舍，提交 `12421a7` 正是去掉了多余的 `Allow-Credentials`。

**结论：不用改。** 但如果以后引入 Cookie 会话，必须同时改成白名单。

### A.6 低：管理端无分页

`worker/src/sites.js:46` / `submissions.js:97` 都是全量 `SELECT *`。18 条数据下这是完全正确的选择，**不要提前优化**。记在这里只为在数据量到 ~2000 条时记得回来加 `?limit=&offset=`。

### A.7 已排除的误报（重要，别去"修"）

审计中有一条被报为 P0 的"批准提交字段名 bug"，称 `worker/index.js:467` 把 `{site_name, site_url}` 当 `{name, url}` 提交、必然失败。**逐行核验后确认是误报。**

`worker/src/submissions.js:105-116` 已经做了映射：

```js
const submissions = pendingSubs.map((sub) => ({
  id: sub.id,
  site: {
    name: sub.site_name,      // ← 映射就在这里
    url: sub.site_url,
    tags: sub.site_tags ? JSON.parse(sub.site_tags) : [],
    ...
```

`sub.site` 的 key 本来就是 `name/url/tags/…`，`handleAdminCreateSite` 收得到。**审核批准流程是通的，不要动。**

> 记这一条的意义：任何"看起来像 bug"的结论都必须核到映射层再下判断，否则会花一天去修一个不存在的问题，而真正会炸的问题（A.1 的 N+1 撞平台限制）反而排在后面。
