> 日期：2026-08-25
> 对象：`broadcast/{index.html,app.js,styles.css}`（918 + 208 + 1275 行）及其内嵌副本 `worker/broadcast-html.js`

> 一句话结论：**前端"粗"的根因有 70% 在数据层。先做 4 个字段的结构化改造，前端才有东西可以发挥；否则再漂亮的组件也只是把空白排得整齐一点。**

## 1. 诊断：为什么现在的前端"发挥不出威力"

### 1.1 用一张图说清根因链

```
checkin 是自由文本（11 种写法）
        └─→ 无法排序、无法比较、无法做区间筛选
                └─→ 前端只能正则猜数字（app.js:497）并统一加"刀"（app.js:518）
                        └─→ 输出错误信息（斑马API 的 100 积分显示成「100 刀」）

字段填充率 11%~78%（models 11%、register 17%、rate 39%）
        └─→ 卡片固定渲染 4 行事实（app.js:535-538）
                └─→ 平均 2.6 行为空 → 卡片高度参差、信息密度低 → "看起来很粗"

标签维度 83% 命中同一个值（非DC 15/18）+ 单选筛选（app.js:29）
        └─→ 筛完还剩 15 条 → 筛选器等于装饰

无鲜度字段展示 + 死链被后端直接过滤（sites.js:96）
        └─→ 用户无法判断可信度 → 不敢点 → 回 TG 问人

单一卡片网格视图（app.js:599-602）+ 无 URL 状态
        └─→ 18 条数据一次性平铺，没有任何"帮我决策"的层次
```

**所以本方案的顺序是：数据结构化（阶段 A）→ 信息架构（阶段 B）→ 交互细节（阶段 C）。跳过 A 直接做 B 是无效劳动。**

## 2. 阶段 A：数据结构化（前端方案的地基，2~3 天）

### 2.1 新增字段（migration `0003`）

```sql
-- UP
ALTER TABLE sites ADD COLUMN slug TEXT;                      -- 稳定主键，改名不丢票
ALTER TABLE sites ADD COLUMN kind TEXT NOT NULL DEFAULT 'api_site';
                              -- api_site | bot | account_pool | tool
ALTER TABLE sites ADD COLUMN quota_min REAL;                 -- 每周期额度下限
ALTER TABLE sites ADD COLUMN quota_max REAL;                 -- 每周期额度上限（无区间时=quota_min）
ALTER TABLE sites ADD COLUMN quota_unit TEXT;                -- usd | cny | credit | coin | token | call
ALTER TABLE sites ADD COLUMN quota_period TEXT;              -- daily | weekly | once | none
ALTER TABLE sites ADD COLUMN quota_calls_est INTEGER;        -- 估算可调用次数（用户真正关心的可比口径）
ALTER TABLE sites ADD COLUMN quota_tier TEXT;                -- high | mid | low | none（人工判定，跨单位可比）
ALTER TABLE sites ADD COLUMN quota_raw TEXT;                 -- 保留原始文本，不丢信息
ALTER TABLE sites ADD COLUMN needs_proxy INTEGER DEFAULT 0;  -- 替代语义模糊的 DC系/半DC/非DC
ALTER TABLE sites ADD COLUMN verified_at TEXT;               -- 最后验证时间（鲜度核心）
ALTER TABLE sites ADD COLUMN verified_by TEXT;               -- admin | healthcheck | community

CREATE UNIQUE INDEX IF NOT EXISTS idx_sites_slug ON sites(slug);
CREATE INDEX IF NOT EXISTS idx_sites_verified ON sites(verified_at);
CREATE INDEX IF NOT EXISTS idx_sites_tier ON sites(quota_tier);
```

**关于 `quota_tier` 为什么必须存在：** `25 刀`、`100 积分`、`1-3 硬币`、`10-20 元` 这四个单位之间没有汇率，程序算不出谁大。硬算就是现在这种"100 积分变 100 刀"的错误。诚实的做法是：机器存 `quota_min/max/unit` 用于**显示**，人工填 `quota_tier` 用于**排序和筛选**。Admin 后台加一个三选按钮，18 条数据 5 分钟填完。

## 3. 阶段 B：信息架构重构（3~4 天）

### 3.1 核心决策：默认视图从"卡片网格"改为"对比表"

**理由不是审美，是数据量和任务类型：**

| | 卡片网格（现状） | 对比表（建议默认） |
|---|---|---|
| 适合的数据量 | 6~12 条 | 15~200 条 |
| 适合的任务 | 浏览、发现（不知道自己要什么） | **比较、决策**（知道要什么，要选最优的那个） |
| 首屏承载 | 3 列 × 2 行 = 6 条（`styles.css:781`） | 15~18 条全部可见 |
| 支持排序 | 弱（要重排整个网格） | 天然（点列头） |
| 字段空值表现 | 卡片高度参差、大片空白 | 单元格留空，**表格自带对齐，空值不刺眼** |

用户来这个站的任务是"选一个今天能用、额度大的"——这是**比较任务**，18 条数据一屏放得下。表格视图直接把"哪个额度最大"变成点一下列头。

**保留卡片视图作为可切换选项**（移动端默认卡片），视图选择写进 URL 和 localStorage。

### 3.2 对比表列定义

| 列 | 内容 | 宽度 | 可排序 | 移动端 |
|---|---|---|---|---|
| 站点 | `name` + `kind` 徽章（🤖机器人 / 🔧工具 / 👤号池）+ 🔒 需魔法图标 | 22% | 按名（zh-CN localeCompare） | 保留 |
| 每日额度 | 主数字 `quota_min~quota_max` + 单位角标；`quota_calls_est` 存在时副行显示"≈60 次调用"；hover / 长按显示 `quota_raw` 原文 | 18% | **按 `quota_tier` 再按 `quota_min`** | 保留 |
| 能力 | `生图` / `限免` 标签（只显示真实存在的） | 12% | — | 折叠 |
| 门槛 | `register`（GitHub / Linux.do / Telegram / 邮箱）；空则显示"—" | 12% | — | 折叠 |
| **鲜度** | `verified_at` 相对时间 + 色阶：≤24h 绿 / ≤7d 黄 / >7d 灰 / 无 显示"未验证" | 12% | **按 `verified_at` 倒序** | 保留 |
| 社区 | 净票数 + 「还能用」计数（来自 feedback） | 10% | 按净票数 | 折叠 |
| 操作 | `访问` 主按钮 + `⋯` 展开详情抽屉 | 14% | — | 保留 |

排序默认值：**`鲜度 desc, quota_tier desc`**——把"最近验证过的高额度站"顶到最上面。这一条比现在的"默认排序"（`sort_order ASC, name ASC`）有价值得多。

### 3.3 筛选器重构：从"一排标签"到"三层筛选"

```
┌─ 第一层：快捷视图（一键达成 80% 需求，chips 单选）────────────────┐
│  [全部]  [今天能签到]  [高额度]  [免费生图]  [无需魔法]  [一次性限免]  │
└──────────────────────────────────────────────────────────────┘
┌─ 第二层：搜索 + 精确条件（默认折叠，点"更多筛选"展开）──────────────┐
│  搜索: [___________]   额度档位: [高][中][低]（多选）                │
│  能力: [生图][限免]（多选，组内 OR）   门槛: [GitHub][TG][邮箱][无]    │
│  类型: [API站][机器人][号池][工具]     ☑ 隐藏 7 天未验证              │
└──────────────────────────────────────────────────────────────┘
┌─ 第三层：结果条 ──────────────────────────────────────────────┐
│  18 条中匹配 6 条  ·  排序[鲜度 ▾]  ·  视图[表格|卡片]  ·  [清除筛选]  │
└──────────────────────────────────────────────────────────────┘
```

快捷视图的实现定义（全部由结构化字段推导，不依赖标签）：

| 快捷视图 | 条件 |
|---|---|
| 今天能签到 | `quota_period === 'daily' && quota_min > 0` |
| 高额度 | `quota_tier === 'high'` |
| 免费生图 | `tags.includes('生图')` |
| 无需魔法 | `needs_proxy === 0` |
| 一次性限免 | `quota_period === 'once'` |

**多选逻辑**：组内 OR，组间 AND。例：`能力=[生图,限免] + 门槛=[GitHub]` → `(生图 OR 限免) AND (register 含 GitHub)`。

**URL 同步**（可分享、可收藏、浏览器前进后退可用）：

```
/?view=table&preset=daily&tier=high,mid&cap=生图&sort=fresh&q=claude&fresh=7
```

用 `URLSearchParams` + `history.replaceState`（筛选变化用 replace 不污染历史，preset 切换用 push）。初始化时从 URL 读回状态——这一条现在完全没有（`app.js` 全文无 `URLSearchParams`）。

**结果条必须带 `aria-live="polite"`**，让屏幕阅读器知道筛选结果变了。现在整个页面 0 处 `aria-live`。

### 3.4 卡片视图的信息分层

现在的卡片把 name / summary / 4 行事实 / notes / tags / 投票 / 反馈**全部平铺**（`app.js:528-587`），这就是"太粗"的直接来源。改为三层：

**L1 —— 决策层（永远可见，3 秒内决定要不要点）**

```
┌─────────────────────────────────────────┐
│ AgentRouter        [API站]  🟢 2小时前验证 │  ← 名称 + 类型 + 鲜度
│                                          │
│      25 刀 / 天          ⭐高额度         │  ← 唯一的大号数字：额度
│                                          │
│ Claude/GPT 全模型，登录即领，需登出重登   │  ← summary（2 行截断）
│                                          │
│ [生图]  🔓无需魔法  GitHub 注册           │  ← 3 个决策标记
│                                          │
│ ┌──────────────┐  👍 12  💬 还能用(8)     │
│ │  访问站点  →  │  ⋯ 详情                 │
│ └──────────────┘                          │
└─────────────────────────────────────────┘
```

**L2 —— 详情抽屉（点"⋯详情"滑出，不跳页）**

放：`quota_raw` 原文、`models`、`rate`、`register` 全文、`notes` 全部、`createdAt/updatedAt`、额度变化历史、投票、反馈入口。

**这一步解决的核心问题**：`models`(11%)、`register`(17%)、`rate`(39%) 这些**低填充率字段全部下沉到抽屉**。卡片正面只放填充率 ≥78% 的字段（name/url/tags/summary/quota），**卡片高度立刻齐平，空白消失**。

**L3 —— 空值处理原则**

| 情况 | 现状 | 改为 |
|---|---|---|
| 字段为空 | `appendFact` 直接跳过（`app.js:425`），留下高度不一致 | 卡片正面不渲染该字段；抽屉里显示"暂无信息 · [补充]"（点击打开反馈表单，`type='correction'`）——**把空白变成 UGC 入口** |
| 额度未知 | 无徽章 | 显示灰色"额度未知 · [告诉我们]" |
| 从未验证 | 无提示 | 灰色"未验证"标记，默认排在最后 |

### 3.5 鲜度与可信度可视化（差异化的关键）

这是竞品（论坛帖 / awesome 列表）做不到的，也是当前前端**完全空白**的部分。

| 元素 | 位置 | 数据来源 | 规则 |
|---|---|---|---|
| 鲜度点 | 卡片头 / 表格列 | `verified_at` | 🟢 ≤24h ／ 🟡 ≤7d ／ ⚪ >7d ／ ⚫ 未验证 |
| 站点级失效标记 | 卡片整体降饱和 + "已失效"角标 | `dead`（`sites.js` 改为输出而非过滤） | 默认折叠到列表底部"已失效 (N)"分组，可展开 |
| 「还能用」/「已失效」按钮 | 卡片底部 | `POST /api/feedback`，`type` 扩展 `still_works` / `dead` | 一键，无需填文本——**这是社区维护鲜度的最低摩擦入口** |
| 全站数据时间 | 页头 | `metadata.updatedAt` | "数据更新于 X 分钟前 · 最近 6 小时自动检测了 18 个链接" |
| 额度变化提示 | 卡片角标 | `site_history`（阶段 3） | "↓ 额度从 25 降到 10（3天前）" |

**为什么"死链隐藏"是错的**：`sites.js:96` 现在把死链直接 filter 掉，用户看到的是"你只收录了 15 个站"。改成展示"3 个已失效"之后，用户看到的是"这个站在认真维护"。**同样的数据，完全相反的信任效果。**

## 4. 阶段 C：交互与工程细节（2 天）

### 4.1 必须消灭前端双副本（这是阶段 0，最优先）

当前 `worker/broadcast-html.js` 是 2237 行手工维护的单字符串，它是**线上唯一来源**（`worker/index.js:696`），而 `broadcast/` 目录已沦为过期备份。

审计初测的逐行 diff：`styles.css` 复制了 100%，`index.html` 96%，`app.js` 只有 **79.5%**——缺的正好是整个反馈系统。手工补齐后现为 **95.3%**（剩余差异是模板字面量转义，函数集合已一致）。

**注意这次是靠人眼发现并手工复制修好的，不是靠工具。** 转义检查（`check-template-escapes.js`）只能验证"语法没坏"，验证不了"内容有没有漏"——它对上次那个丢了 161 行的版本会全部通过。

**方案：`scripts/build-html.js`（约 40 行）**

```js
// 读 broadcast/{index.html,styles.css,app.js}
// 1. 把 <link rel="stylesheet" href="./styles.css"> 替换为 <style>…</style>
// 2. 把 <script src="./app.js" defer> 替换为 <script>…</script>
// 3. 转义反引号、${、以及裸 \ （沿用 scripts/check-template-escapes.js 已有的规则）
// 4. 输出 worker/broadcast-html.js：export const broadcastHtml = `…`;
```

配套三件事：
- `scripts/deploy.sh` 里 `wrangler deploy` **之前**强制执行 build
- `worker/broadcast-html.js` 文件头加 `// AUTO-GENERATED by scripts/build-html.js — DO NOT EDIT`
- 加一个防回归检查：`node scripts/check-html-sync.js` 比对生成结果与仓库中文件是否一致，不一致则退出码非 0

**顺手补一个已有的检查漏洞**：`scripts/deploy.sh` 原先只对 `worker/index.js` 跑转义检查，漏掉了 `worker/broadcast-html.js`（2237 行、包含全部前端 JS、转义风险最高的那个文件）。

> **更新**：这一点已于 2026-08-25 21:44 修好，`deploy.sh` 现在两个文件都检查；`docs/10_部署规范与闭环审查_2026-08-25.md` 记录了该规范。
>
> 但要分清两件事：**转义检查保证"生成的 JS 语法不坏"，构建脚本保证"内容不漏"。** 这是两个不同的问题——前者已解决，后者仍未解决。`check-template-escapes.js` 对那个丢了 161 行反馈代码的版本会 100% 通过，因为剩下的代码语法完全正确。

> 不做构建脚本这件事，后面所有前端改动都会**再丢一次功能**。这次是靠人眼发现的，下次不一定有人看。

### 4.2 前端代码结构（保持原生 JS，不引入框架）

**为什么不上 Vue/React**：产物必须内联进 Worker 的单字符串（30~50KB 是舒适上限），一个框架 runtime 就吃掉全部预算；数据量 18~200 条，原生 DOM 完全够；团队现在没有构建链，引入框架等于引入 node_modules + bundler + 新的转义坑。

**但要拆模块**，由 build 脚本按序拼接（不需要 bundler）：

```
broadcast/src/
  00-config.js     # 常量、字段元信息、快捷视图定义、单位显示映射
  10-state.js      # state + URL 同步（读写 URLSearchParams）
  20-api.js        # fetch 封装、错误归一、单次请求（去掉 /api/votes）
  30-filter.js     # matches() / sort() / 派生统计
  40-view-table.js # 表格视图
  50-view-card.js  # 卡片视图 + 详情抽屉
  60-forms.js      # 提交 / 反馈（由 schema 驱动字段，见 4.4）
  70-ui.js         # toast / skeleton / theme
  99-boot.js       # 初始化
```

`build-html.js` 按文件名排序拼接进一个 IIFE。**零依赖、零 bundler、可读性回归。**

```json
{
  "ok": true,
  "metadata": {

  },
  "sites": [{

    "kind": "api_site",

    "quota": {
      "min": 25, "max": 25, "unit": "usd", "period": "daily",
      "callsEst": null, "tier": "high",

```

要点：
- `quota` 收成嵌套对象，前端一处读取

- `signals` 让"社区说还能用"可展示
- 前端不再需要 `/api/votes`
