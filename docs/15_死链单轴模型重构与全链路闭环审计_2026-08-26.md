## 一、最终模型（现行代码事实）

```
证据层（只观测，永不改状态）              决定层（唯一状态入口）
├─ cron 每6h切片探活                     管理员操作：
│   成功→verified_at='healthcheck'       ├─ 单站开关（PUT /sites/:name）
│        fail_count=0                    ├─ 批量 enable/disable
│   失败→fail_count+1，不写鲜度          ├─ 遗留黑名单移除联动
│   永不触碰 enabled                     └─ （全部写入 verified_by='manual'
├─ 手动批量检查 check-batch                    + 启用时清零 fail_count）
│   纯只读，响应无 restored/newDeadUrls
└─ 用户反馈 still_works                  派生：dead := enabled !== 1
    verified_by='feedback'               公开页全量展示，死链折叠「已失效」组
```

不变量（均有测试锁定）：
1. 失败绝不被自动禁用；成功也绝不被自动启用（test-api 组12）
2. 一切状态变更写人工验证戳并清零失败计数（test-api 组11）
3. 公开 API 返回全量站点，前端不得按 enabled 裁剪（test-frontend 组2 回归锚点）
4. URL 尾斜杠容差仅存在于遗留黑名单匹配（rtrim），主链路用规范化 URL

## 三、静态一致性审计方法与结论（可复现）

- 内联 handler 全量清点：44 处，零字符串参数注入陷阱（动态参数走 data-*）
- 43 个被内联引用的函数：全部存在定义
- getElementById 52 个引用 vs id= 定义：差集为空
- data-action 发射 vs click/change 委托处理：差集为空
- 前端 api() 10 类端点 × 后端 ===路由 + 3 条正则路由（sites/:name PUT·DELETE、submissions approve、feedbacks/:id POST）：全覆盖，方法匹配
- 新增 HTML 插值 esc() 覆盖：唯一裸插值为数值型 healthFailCount（无注入面）
