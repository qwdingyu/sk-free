## 一、铁律：部署必须走 `bash scripts/deploy.sh`

### 1.1 规则

```bash
# ✅ 唯一正确的部署方式
bash scripts/deploy.sh

# ❌ 一律禁止
npx wrangler deploy
cd worker && npx wrangler deploy
```

### 1.2 deploy.sh 当前 8 步流水线（与 HEAD 核对）

| 步骤 | 检查/动作 | 拦的是什么 |
|------|----------|-----------|
| 1 | `node --check` 全部 JS | 语法错误 |
| 2 | `check-api-contract.js` | 前端读的字段与后端 formatSiteRow 产出不一致（snake_case/camelCase 错配 → 整列"额度未知"，不抛错） |
| 3 | `check-css-coverage.js` | JS createElement 出的 class 在 styles.css 里没有规则（抽屉无定位飘到页脚，不抛错） |
| 4 | `build-html.js`（tee 捕获 BUILD_ID） | 构建 + 转义往返验证 + 内联脚本语法检查 |
| 5 | `test-frontend.mjs`（jsdom 行为回归） | 页面照样渲染、功能静默失效（5+1 类 bug 清单见 §五） |
| 6 | `check-template-escapes.js`（index.js + broadcast-html.js 两个文件） | 模板字面量转义把 `<script>` 写坏 |
| 7 | `wrangler deploy` | 部署 |
| 8 | `verify-deploy.sh "$BUILD_ID"` | 部署后断言线上 = 刚构建的产物 |

脚本头必须 `set -e` + `set -o pipefail`。**pipefail 不是可选项**：第 4 步用 `node build-html.js | tee` 同时保留输出与捕获 BUILD_ID，没有 pipefail 时管道退出码是 tee 的（永远 0），构建失败会被一路带到 `wrangler deploy`——正好是本脚本要防的事。

### 1.3 为什么不能直接 wrangler deploy

历史事实：`worker/broadcast-html.js` 与 `broadcast/` 曾是**手工双副本**，新增前端功能漏同步导致线上功能丢失（反馈弹窗 `grep -c feedbackModal → 0`，见 docs/10）。build-html.js 消灭双副本后，任何绕过 deploy.sh 的部署都会跳过构建，等于投回旧版。

## 二、部署产物一致性（血泪案例与机制）

### 2.1 案例：线上缺抽屉 CSS，根因有两处误读

现象：表格模式点「⋯」，弹窗没有任何定位地出现在页脚下方（无遮罩、无滑入动画）。

**误读一（错误归因）**："线上跑的是旧 bundle"。错误的。
用 `git log -S".drawer-overlay" -- broadcast/styles.css` 查证：这条字符串只出现在 **621a738**（补上抽屉样式的那次提交）。抽屉 CSS **从来没被写过、因而从未存在**，不是"写过又没部署"。归因错误会让下一个人去追一个不存在的缓存问题。

**误读二（机制缺失）**：即使真有"旧 bundle"，当时 deploy.sh 结尾只有三条**打印出来不执行**的 curl 提示——部署动作本身对"线上到底是不是新产物"没有任何断言。

### 2.2 机制 1：构建标识用内容哈希，不用时间戳

```javascript
// scripts/build-html.js
const BUILD_ID = createHash("sha256").update(result).digest("hex").slice(0, 12);
// 注入 HTML：<!-- build:<sha256前12位> -->
```

为什么不是 ISO 时间戳（第一版就是时间戳，已被废弃）：

| 维度 | 时间戳（已废弃） | 内容哈希（现行） |
|------|-----------------|-----------------|
| git status | 每跑一次构建产物就变，真改动被噪音埋掉 | 源码未变则产物逐字节相同（实测两次构建同 hash 同 sha256） |
| 断言强度 | 只能证明"构建过" | 能证明"线上内容 == 本地内容" |

### 2.3 机制 2：转义往返验证——可证明的不变量，不是启发式

build-html.js 内建（转义后立即执行）：

```
把产物写到 tmpdir 的 .mjs 副本 → import 回来 → broadcastHtml
   与转义前的原文 rawHtml 逐字符比对
```

相等 ⇒ 转义在这份具体内容上可逆，**不需要任何启发式判断**。不相等 ⇒ 定位首个差异字符并打印上下文后 `fail()`。

**负向测试（证明机制真的能拦）**：注释掉经典顺序 bug `result.replace(/\\/g, "\\\\")` 后，构建立即失败并定位到第 57626 个字符：

```
原文  /[+-]\d{2}:?\d{2}$/
产物  /[+-]d{2}:?d{2}$/
```

正是 `parseUtc` 的时区正则丢掉反斜杠、变成**永不匹配**。语法完全合法，`node --check` 一定放过——只有往返比对能抓到。

技术细节：用 `.mjs` 临时副本做 import，而不是直接 import 产物——`worker/package.json` 没有 `"type":"module"`，直接 import 会每次都打一行 MODULE_TYPELESS 警告。

### 2.4 机制 3：内联脚本语法检查必须对"求值后"的内容、且遍历每一个 `<script>`

浏览器解析的是**求值后**的 broadcastHtml 里的 `<script>` 内容。对转义形态做 node --check 是检查错了对象：单反斜杠的 `\n` 在转义形态里是合法的两字符转义序列，求值后才变成真换行并炸掉字符串。

两个坑（都修过）：

| 坑 | 错误表现 | 修复 |
|----|---------|------|
| 只匹配 `<script>` | 产物内联的是 `<script defer>`，永远提取不到 → 语法检查是假的"通过" | `<script([^>]*)>`，过滤带 `src=` 的外链 |
| 只查第一个 `<script>` | 命中的是页面头部几百字节的主题预设脚本，**58 KB 的主 bundle 从来没被检查过**（实测 0.7 KB vs 58.4 KB） | `matchAll` 遍历每一个 |

## 三、检查工具的"空检查假阳性"教训：必须做负向测试

### 3.1 事例：check-template-escapes.js 曾经对广播产物报"0 个区域 ✅ 通过"

- 模板区域检测只认 `return \``——广播产物是 `export const broadcastHtml = \``，检测不到
- `<script>` 正则匹配不到 `<script defer>`
- **结果：对线上最危险的产物文件，这个检查什么都没查，打印的"✅ 通过"是假的**

规则：**任何检查脚本，上线前必须做负向测试**——故意注入它声称要拦的错误，确认它真的非零退出。本文档所有机制都这样做过（§2.3 的往返比对、§3.2 的策略 1 判据、§4.2 的 verify-deploy 断言）。

### 3.2 策略 1 判据的演进：从"引号数"到"字符串内部扫描"

初代判据：单反斜杠 + **该行引号总数为奇数**（字符串跨行）。太窄，漏掉典型形态：

```javascript
const BAD = "line1\nline2";
```

引号配对（偶数）、单反斜杠——模板求值后 `\n` 变真换行、字符串未终止、整块 `<script>` 解析失败。实测初代判据对这一行报"✅ 通过"。

现行判据：从行首扫描引号状态（跳过被转义字符），判断该反斜杠是否**落在字符串字面量内部**。负向测试：注入上面那行，准确报行号 + 修复建议；两个真实文件无误报。

### 3.3 模板字面量转义的产物形态（写检查脚本前必须知道）

build-html.js 只转义 **result 内容**（HTML/CSS/JS），模板定界符保持未转义：

```
文件里只有 2 个未转义反引号：打开（export const broadcastHtml = `）与关闭（`;）
内容里的反引号全部是 \` 转义形态
```

检测广播产物的区域边界：开始行用行首锚定 `^\s*export\s+const\s+\w+\s*=\s*\``（**不能锚定行尾**——内容从同一行的反引号后就开始）；结束取开始之后**最后一个** `` `; ``（内容里也可能出现 `\`;`，取第一个会截断区域）。

反转义（策略 2 提取 script 前）必须按构建顺序的**逆序**：先 `\${` → `${`，再 `` \` `` → `` ` ``，最后 `\\` → `\`。

## 四、部署后自动验证（verify-deploy.sh）

### 4.1 职责

`wrangler deploy` 成功返回 ≠ 线上跑的是刚构建的产物。可能的原因：边缘节点传播中、别的会话改了源码、部署到别的 environment。这些链路本身都不报错，只有用构建标识对线上做断言才能兜住。

### 4.2 断言必须挑"只有目标产物才可能包含"的字符串

**真实假阳性案例**：最初断言线上包含 `.drawer-overlay` 来证明抽屉样式在——但内联 JS 里本来就有 `document.querySelector(".drawer-overlay")`，所以 CSS 规则一条都没有时这条断言照样 `[OK]`。实测：拿 drawer CSS 完全缺失的构建产物，它仍然通过。

现行断言全部用 CSS 专有形态（JS 从不写这些组合）：

```
.drawer-overlay.open / .drawer-overlay { / .drawer-close { / .drawer-title { / .dead-group {
```

负向测试：对抽屉 CSS 缺失的产物五条全部 FAIL，对当前产物全部 OK。

### 4.3 边缘传播重试

一次 curl 失败就打印"考虑回滚"是过度反应——**回滚一个其实正常的部署，风险比多等 12 秒大得多**。只对构建标识做有限重试（最多 4 次 × 4 秒），其余断言不做重试。

### 4.4 bash 多字节词法坑（写部署脚本的铁律）

本机 bash 在双引号字符串里写 `"$URL，..."`（变量后**紧贴**全角标点）时，会把全角字符的第一个字节并入变量名：

```bash
# ❌ set -u 下报：URL<某字节>: unbound variable（变量明明赋值了）
echo "🔎 部署后验证（$URL，构建标识 ${BUILD_TS}）..."

# ✅ 花括号形式，或与中文间留空格/改用 ASCII 标点
echo "🔎 部署后验证: URL=${URL} BUILD_TS=${BUILD_TS} ..."
```

实测：`echo "debug URL=[$URL]"`（纯 ASCII 上下文）正常，下一行 `$URL` 后紧跟全角逗号就炸。`export LC_ALL` 无效（bash 5.3 亦然）。**规则：shell 脚本里任何变量展开都要用 `${VAR}`，或确保后一个字符是 ASCII。**

## 五、静默失效 bug 模式清单（test-frontend.mjs 的由来）

这一类 bug 的共同点：**代码不报错、页面照样渲染、功能静默失效**。看代码很难发现，跑一遍真实 DOM 立刻暴露。jsdom 行为回归测试（35 项断言）把下面每个模式都固化成断言：

| # | 模式 | 发生过的具体形态 | 防它的断言 |
|---|------|-----------------|-----------|
| 1 | 过滤条件把自己依赖的 UI 过滤掉（死锁） | `matchesFilters` 过滤死链 → dead 数组恒空 → "已失效"展开按钮永不渲染 → `showDead` 永远没有入口翻成 true，死链分组整套不可达 | 展开按钮存在、分组可展开、`"匹配 N 条"只数活链` |
| 2 | 重渲染回调重建了带状态的面板 | chip 点击调 `renderFilters()`，第一行 `innerHTML=""` 重建整条筛选栏，展开面板是局部变量 → 每点一个筛选项面板就收起，多选组实际没法多选 | 点选筛选项后面板仍展开、chip aria-pressed 已翻转 |
| 3 | 计数算在别的渲染函数里 | 结果计数在 `renderFilters()` 里算，筛选变化只调 `renderResults()` → 列表只剩 1 条还写着"匹配 18 条" | 结果计数已刷新 |
| 4 | 监听器只在一条关闭路径注销 | 抽屉 onKey 挂 document、只在 Escape 分支注销 → 从 ✕/遮罩关闭时永久留存，开关 8 次泄漏 8 个；此后按 Escape 触发全部陈旧监听器，焦点跳到几个抽屉之前 | 经 close/overlay/escape 各关 5 次后无残留 keydown 监听器 |
| 5 | 字段名错配（前后端契约） | 前端读 snake_case 而 API 返回 camelCase → 18/18 显示"额度未知" | 高/中/未知额度站各显示正确文本 |
| 6 | 非法 HTML 结构 | `<tr>` 直接子元素是 `<div>` → HTML 解析器 foster parenting 把 div 移出表格，表格塌成一堆卡片；`<tbody>` 嵌套 `<tbody>` | 表格行直接子元素全是 TD、每行 7 单元格、`tbody tbody` 数量为 0 |
| 7 | a11y 状态写死 | aria-sort 一律 descending 但按名称是升序；展开按钮 aria-expanded 写死 false 与 state 脱节 | aria-sort 跟随真实排序、表格不声明 role=grid（未实现方格键盘导航就不承诺） |

配套机器检查：`check-css-coverage.js` 扫 JS 产出的 class，逐个核对 styles.css 有无规则（当前 78 个 class 全覆盖）。缺失的 class 会让元素以无定位普通块渲染——JS 和 CSS 都不报错，只有机器核对能兜住。

## 六、时区与数据契约

- **D1 时间戳按 UTC 解析**：`verifiedAt` 存 UTC，前端解析必须 `parseUtc`，否则"刚写入"显示成"8小时前"。
- **单位换算不要跨单位比较**：`100 积分` 和 `25 刀` 的数字大小没有可比性，额度档位内的次级排序用与单位无关的鲜度。
- **NaN 不允许流进比较器**：验证时间缺失/解析失败按 0 处理（单独抽出 `verifiedTs()`），否则 sort 结果依赖原始顺序，表现为"刷新一次顺序就变了"。

## 七、并行会话/多人协作时的提交纪律

本目录的文档与脚本经历过两轮并行修改，都导致了信息/状态滞后：

| 现象 | 教训 |
|------|------|
| 源码已修复（621a738 等 4 个 commit 已提交）但**从未部署**，线上继续跑旧代码，用户看到抽屉缺样式 | 提交 ≠ 部署。功能修复提交后要立即走 deploy.sh，并在本会话内用 verify-deploy.sh 确认 |
| 构建标识方案在几十分钟内从时间戳演进为内容哈希（3c1181c），写文档的人若不读当前代码就会写出过时方案 | **写文档/报告/建议前必须读当前代码**（git log + read 文件），不凭记忆；HEAD 在会话中途可能已经前移（本文档写作时 HEAD = 3c1181c，其本身也尚未部署，本地 `build:015fef7c05c7` vs 线上无哈希标识） |
| 检查脚本的"✅ 通过"可能是空检查 | 检查脚本必须有负向测试证据才能宣布"能防住" |

**通用规则**：
1. 引用任何脚本/函数/字段前，`git log` / grep 确认它存在且是当前形态
2. 部署前后各核对一次 HEAD 与线上构建标识
3. 每次机制性修复附带负向测试结果（写进 commit message 或文档）
