# 04 站点管理后台使用说明

> 日期：2026-08-24
> 状态：待部署

## 一、功能概述

sk-free 管理后台是一个嵌入在 Cloudflare Worker 中的 Web 界面，提供对 `sites.json` 数据的完整 CRUD 和批量操作能力。

### 核心功能

| 功能 | 说明 |
|------|------|
| 🔐 登录认证 | Bearer Token 认证，密码存储在 Worker Secret 中 |
| 📋 站点列表 | 表格展示所有站点，支持搜索和标签筛选 |
| ⚡ 启用/停用 | 每个站点可独立启用或停用，停用后前端不展示 |
| ➕ 新增站点 | 表单填写站点信息，自动校验必填项 |
| ✏️ 编辑站点 | 点击编辑按钮，预填现有数据，修改后保存 |
| 🗑️ 删除站点 | 单个删除，带确认提示 |
| 🏷️ 批量打标签 | 勾选多个站点，批量添加标签 |
| ✅/⛔ 批量启用/停用 | 勾选多个站点，批量启用或停用 |
| 🗑️ 批量删除 | 勾选多个站点，批量删除 |
| 📥 批量导入 | 导入 JSON 文件，自动剥离 aff/ref/invite 等推广参数，以干净 URL 去重，保留原始 URL |
| 📤 导出 | 下载完整 sites.json 文件 |
| 📝 提交审核 | 查看用户通过首页提交的新站点，支持批准或驳回 |
| 🔄 刷新 | 从 KV 重新加载最新数据 |

### 技术架构

```
┌─────────────────────────────────────────────┐
│           管理页面（Worker 内嵌 HTML）        │
│           https://xxx.workers.dev/admin      │
│                                              │
│  登录 → Bearer Token → localStorage         │
│  操作 → /api/admin/* → KV 读写              │
└──────────────────┬──────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────┐
│        Cloudflare Workers KV                │
│        Key: "sites.json"                    │
│        Value: { metadata, sites[] }         │
└──────────────────┬──────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────┐
│     前端页面（GitHub Pages）                  │
│     GET /api/sites → 从 KV 读取站点数据      │
│     GET /api/votes → 从 KV 读取投票数据      │
└─────────────────────────────────────────────┘
```

## 二、首次部署

### 2.1 前提条件

- 已执行 `npx wrangler login` 登录 Cloudflare
- 已创建 KV 命名空间（deploy.sh 会自动创建）

### 2.2 设置管理密码

```bash
cd worker/

# 设置 ADMIN_TOKEN（管理密码）
npx wrangler secret put ADMIN_TOKEN
# 输入一个强密码（如：my-s3cret-adm1n-p@ss）
```

### 2.3 部署 Worker

```bash
npx wrangler deploy
```

部署完成后会显示管理页面地址，如：
```
📋 管理页面：https://sk-free-vote.xxx.workers.dev/admin
```

### 2.4 初始数据导入

首次部署后 KV 中没有站点数据，需要导入：

**方式一：通过管理页面导入（推荐）**

1. 访问 `/admin`，输入管理密码登录
2. 点击 **📥 导入** 按钮
3. 选择本地 `broadcast/data/sites.json` 文件
4. 确认导入（自动去重，支持覆盖模式）

**方式二：通过 API 导入**

```bash
curl -X POST https://sk-free-vote.xxx.workers.dev/api/admin/sites/import \
  -H "Authorization: Bearer YOUR_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"sites":'"$(node -e "console.log(JSON.parse(require('fs').readFileSync('broadcast/data/sites.json')).sites)")"'}'
```

**方式三：手动写入 KV**

```bash
npx wrangler kv:key put --namespace-id <id> sites.json "$(cat broadcast/data/sites.json)"
```

## 三、日常使用

### 3.1 访问管理页面

浏览器打开 `https://sk-free-vote.xxx.workers.dev/admin`，输入管理密码登录。

登录状态保存在浏览器 localStorage 中，关闭页面后再次打开无需重新登录。

### 3.2 新增站点

1. 点击 **➕ 新增** 按钮
2. 填写站点信息（名称和 URL 为必填）
3. 点击 **保存**

### 3.3 编辑站点

1. 在站点列表中找到目标站点
2. 点击 **编辑** 按钮
3. 修改需要更新的字段
4. 点击 **保存**

### 3.4 删除站点

1. 点击站点行的 **删除** 按钮
2. 确认删除

### 3.5 批量操作

1. 勾选需要操作的站点（支持全选）
2. 使用批量操作栏：
   - **🏷️ 批量打标签**：输入标签名称，为所有选中站点添加该标签
   - **🗑️ 批量删除**：删除所有选中站点

### 3.6 导入站点

1. 点击 **📥 导入** 按钮
2. 选择 JSON 文件（支持 `{ sites: [...] }` 或 `[...]` 两种格式）
3. 预览导入数据，确认数量
4. 可选：勾选"覆盖已存在的同 URL 站点"
5. 点击 **开始导入**

**智能 URL 解析**：导入时会自动剥离 URL 中的 `aff`、`ref`、`invite` 等推广参数，以干净 URL 去重。被剥离的参数存入站点的 `ref` 字段，方便后续替换为自己的邀请码。

**适用场景**：从其他站点导航项目批量导入站点数据时，无需手动清理 URL。

### 3.7 导出数据

点击 **📤 导出** 按钮，浏览器会下载当前 KV 中的完整 sites.json 文件。

### 3.8 搜索和筛选

- **搜索框**：输入关键词，实时过滤站点（匹配名称、URL、标签、摘要等）
- **标签筛选**：下拉选择特定标签，只显示该标签的站点

## 四、API 接口

### 4.1 公开接口（无需认证）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/sites` | 获取站点列表（仅已启用站点，前端渲染用） |
| POST | `/api/submit` | 用户提交新站点（待审核） |
| GET | `/api/votes` | 获取投票数据 |
| POST | `/api/vote` | 提交投票 |
| GET | `/api/health` | 健康检查 |

### 4.2 管理接口（需 Bearer Token）

```bash
# 所有管理接口需要在请求头中携带 Token
Authorization: Bearer <ADMIN_TOKEN>
```

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/admin/sites` | 列出所有站点（含 disabled） |
| POST | `/api/admin/sites` | 创建新站点 |
| POST | `/api/admin/sites/import` | 批量导入站点（智能 URL 解析 + 去重） |
| PUT | `/api/admin/sites/:name` | 更新站点（含 enabled 切换） |
| DELETE | `/api/admin/sites/:name` | 删除站点 |
| POST | `/api/admin/sites/batch` | 批量操作（delete/tag/enable/disable/approve/reject） |
| GET | `/api/admin/submissions` | 查看待审核提交列表 |
| GET | `/api/admin/export` | 导出完整 sites.json |

### 4.3 批量操作参数

```json
{
  "action": "delete" | "add_tag" | "remove_tag" | "enable" | "disable",
  "names": ["站点名1", "站点名2"],
  "tag": "标签名"  // add_tag/remove_tag 时必填
}
```

**提交审核操作：**
```json
{
  "action": "approve_submission" | "reject_submission",
  "id": "提交ID"
}
```

### 4.4 批量导入参数

```json
{
  "sites": [
    { "name": "站点名", "url": "https://...?aff=XXX", "tags": ["签到"], "summary": "..." },
    { "name": "站点名2", "url": "https://...?ref=YYY", "tags": ["生图"] }
  ],
  "overwrite": false
}
```

**智能 URL 解析规则：**
- 自动剥离 URL 中的 `aff`、`ref`、`invite`、`invite_code`、`start` 查询参数
- 剥离后的干净 URL 作为唯一标识（去重依据）
- 被剥离的参数存入站点的 `ref` 字段（如 `aff=FWQS`）
- 示例：`https://api.example.com/signup?aff=FWQS&ref=abc` → URL 变为 `https://api.example.com/signup`，ref 字段为 `aff=FWQS`

**响应：**
```json
{
  "ok": true,
  "imported": 10,
  "added": 8,
  "updated": 0,
  "skipped": 2,
  "duplicates": [
    { "name": "已存在的站点", "url": "https://...", "existingName": "已存在的站点" }
  ]
}
```

**限制：** 单次最多导入 200 条（保护 Worker CPU 时间不超过 10ms 限制）。

### 4.5 创建/更新站点参数

```json
{
  "name": "站点名称（必填）",
  "url": "https://...（必填）",
  "tags": ["签到", "生图"],
  "summary": "站点摘要",
  "checkin": "每日签到 5-50 刀",
  "models": "Claude Opus 5、GPT-5.6",
  "rate": "0.1",
  "register": "GitHub",
  "ref": "aff=FWQS",
  "originalUrl": "https://...?aff=FWQS",
  "notes": ["备注1", "备注2"],
  "enabled": true
}
```

**字段说明：**
- `enabled`: 是否在前端展示（默认 `true`），设为 `false` 可隐藏站点但不删除
- `originalUrl`: 导入时自动保留的原始 URL（含推广参数），用于溯源
- `ref`: 从 URL 中剥离的推广参数（如 `aff=FWQS`）

### 4.6 速率限制

管理 API 基于 IP 的滑动窗口速率限制：

| 参数 | 值 | 说明 |
|------|-----|------|
| 窗口 | 10 分钟 | 滑动窗口 |
| 限制 | 100 次/IP/窗口 | 超出返回 429 |
| 存储 | 内存（Map） | Worker 重启后重置，无需 KV |

超限时返回：
```json
{ "ok": false, "error": "管理 API 请求过于频繁，请 XX 秒后再试" }
```

### 4.7 用户提交接口

```bash
POST /api/submit
Content-Type: application/json

{
  "name": "站点名称",
  "url": "https://...",
  "tags": ["签到"],
  "summary": "站点简介",
  "checkin": "每日签到 5-50 刀",
  "models": "Claude Opus 5",
  "register": "GitHub"
}
```

**速率限制：** 每 IP 每天最多 5 次提交。

**响应：**
```json
{ "ok": true, "message": "提交成功，等待管理员审核" }
```

提交后存入 `submissions.json`，管理员在后台「提交审核」标签页中审核。批准后站点自动添加到列表。

## 五、安全说明

### 5.1 认证机制

- 管理密码存储在 Cloudflare Worker Secret 中（`ADMIN_TOKEN`）
- 前端通过 `Authorization: Bearer <token>` 头传递密码
- 密码不会出现在 URL、日志或 Worker 代码中
- 登录状态仅保存在浏览器 localStorage 中

### 5.2 安全建议

1. **使用强密码**：ADMIN_TOKEN 建议 16 位以上，包含大小写字母、数字和特殊字符
2. **定期更换**：建议每 3-6 个月更换一次管理密码
3. **不要分享**：管理密码等同于站点数据的完全控制权
4. **检查访问日志**：可通过 `wrangler tail` 查看 Worker 的实时请求日志

### 5.3 更换管理密码

```bash
cd worker/
npx wrangler secret put ADMIN_TOKEN
# 输入新密码
npx wrangler deploy
```

## 六、数据同步

管理后台修改的数据直接写入 Cloudflare KV，这是站点数据的**唯一真实来源**。

### 6.1 KV → GitHub 同步

管理后台修改数据后，本地的 `broadcast/data/sites.json` 不会自动更新。如需同步：

```bash
# 方式一：通过管理页面导出，替换本地文件
# 1. 在管理页面点击"导出"
# 2. 用下载的文件替换 broadcast/data/sites.json

# 方式二：通过 API 下载
curl -H "Authorization: Bearer <TOKEN>" \
  https://sk-free-vote.xxx.workers.dev/api/admin/export \
  > broadcast/data/sites.json

# 然后提交到 GitHub
bash deploy.sh
```

### 6.2 GitHub → KV 同步

如果直接修改了 GitHub 仓库中的 `sites.json`（通过 PR 或直接编辑），需要手动同步到 KV：

```bash
# 通过导入 API（推荐，自动去重）
curl -X POST https://sk-free-vote.xxx.workers.dev/api/admin/sites/import \
  -H "Authorization: Bearer <TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"sites":'"$(node -e "console.log(JSON.parse(require('fs').readFileSync('broadcast/data/sites.json')).sites)")"',"overwrite":true}'

# 或通过管理页面导入
# 1. 在管理页面点击"导入"
# 2. 选择 broadcast/data/sites.json
# 3. 勾选"覆盖已存在的同 URL 站点"
# 4. 确认导入
```

## 七、常见问题

### Q: 管理页面打不开？

A: 检查以下几点：
1. Worker 是否部署成功：`npx wrangler tail`
2. URL 是否正确：`https://<worker-name>.workers.dev/admin`
3. 浏览器控制台是否有 CORS 错误

### Q: 登录提示"未授权"？

A: 检查 ADMIN_TOKEN 是否正确设置：
```bash
cd worker/
npx wrangler secret list  # 确认 ADMIN_TOKEN 存在
npx wrangler secret put ADMIN_TOKEN  # 重新设置
npx wrangler deploy  # 重新部署
```

### Q: 前端页面数据没有更新？

A: 前端从 Worker API 获取数据，确保：
1. `app.js` 中的 `VOTE_API_URL` 已填入正确的 Worker 地址
2. 前端代码已部署到 GitHub Pages
3. 浏览器缓存已清除（Ctrl+Shift+R）

### Q: 批量操作失败？

A: 检查：
1. 请求体格式是否正确（JSON）
2. 站点名称是否完全匹配（区分大小写）
3. 标签名称是否正确（add_tag/remove_tag 需要 tag 参数）

## 八、与前端页面的关系

| 数据源 | 说明 |
|--------|------|
| `broadcast/data/sites.json` | GitHub 仓库中的静态数据（已过时，仅作备份） |
| Worker KV `sites.json` | **权威数据源**，管理后台和前端都从此读取 |
| Worker KV `votes.json` | 投票数据 |

**重要**：管理后台修改的是 KV 中的数据，不是 GitHub 仓库中的文件。如果需要将 KV 数据同步回 GitHub 仓库，参见第六节。
